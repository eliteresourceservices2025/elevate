# ELEVATE — instructions for Claude Code

ELEVATE (ELITE Employee & VA Engagement / Talent Experience) is the internal HRIS for Elite Resource Services (ERS), a Philippine VA staffing company with 125+ employees and VAs, many serving US healthcare clients. It holds sensitive personal data. **Security and privacy rules below are non-negotiable; if a request conflicts with them, stop and ask.**

The full design is in `docs/architecture-plan.md`. Read the relevant section before starting a module. Build order: `docs/BUILD-PROMPTS.md`; environment: `docs/SETUP.md`.

## Architecture rules

1. **Modular monolith.** Each module lives in `src/modules/<module>/` with `schema.ts`, `actions.ts`, `queries.ts`, `validators.ts`, `permissions.ts`, `components/`. A module never imports another module's `schema.ts` directly for writes; call that module's exported functions.
2. **Server Components by default.** Add `"use client"` only for interactivity. No Redux/Zustand; URL state via `nuqs`; TanStack Query only for live-refresh grids.
3. **All data access is server-side through Drizzle** (`src/lib/db.ts`, which imports `server-only`). Never query app tables with supabase-js from the browser. supabase-js is used only for auth and signed storage URLs.
4. **Every server action and query starts with** `const user = await requireUser()` (AAL2 enforced) and `await authorize(user, "<module>.<action>", resource)`. Hiding a button is never the only guard.
5. **Validate every input with Zod on the server**, even if the form already did.
6. Leave balances come only from the append-only `time.leave_ledger`; never store a mutable balance number.
7. Use soft delete (`archived_at`); never hard-delete employee records except through the retention job.
8. Dates: store `timestamptz` in UTC; display in the viewer's zone; schedules also show the client's zone. Use `date-fns-tz`.
9. **Time and attendance: ELEVATE is the time clock and the only source of hours.** `time.clock_events` is append-only (clock_in, break_start, break_end, clock_out); corrections are new rows with a reason and lead approval, never edits. Timestamps come from the server clock and the IP from the request, never from values the browser sends. Location is optional, needs the employee's permission, and is stored rounded (~1 km). `time.attendance_days` is always rebuilt from clock events, never edited by hand.
10. **Jibble is used only for screenshots.** On clock-in/clock-out, ELEVATE mirrors the event to Jibble through its API (queued in Inngest, retried, logged in `time.jibble_link_log`). Never read hours from Jibble into payroll exports, and never copy Jibble screenshots, GPS or activity data into ELEVATE: screenshots can contain client patient data.

## Database connection (do not remove the query limiter)

- `src/lib/db.ts` wraps the driver with `limitQueries` (`src/lib/limit-queries.ts`): **at most 6 queries run at once, the rest wait in the app**, never inside the driver. Reason: behind Supabase's transaction pooler (Supavisor, port 6543, which production uses) a driver that queues more queries than it has connections stalls the pooler: a server connection sits `active` in `ClientRead` until the 2-minute statement timeout, and every other query waits behind it, so a page that asks for 20+ things at once (the dashboard) froze for minutes. Proven with a plain script: 30 parallel queries hung, 150 through the limiter took 0.5 s. Settings that did NOT help: `max`, `max_pipeline`, `prepare`, `fetch_types`.
- The limit is below `max: 10` connections on purpose, so transactions (`db.transaction` reserves a connection) still find one free. Keep it that way when changing either number.
- **To reproduce pooler problems locally:** set `[db.pooler] enabled = true` in `supabase/config.toml` (`default_pool_size = 15` matches the free plan), `supabase stop` then `supabase start`, and run the app with `DATABASE_URL=postgresql://postgres.pooler-dev:postgres@127.0.0.1:54329/postgres`. Dashboard panels also time out after 20 s (`guarded`), so a database stall shows a notice instead of a frozen page.

## Organization and team scope

- Who reports to whom and which team someone is in are **dated** (`core.reporting_lines`, `core.team_memberships`); `employees.manager_id/team_id` hold the current values. Change them only through `applyReporting()` in `src/modules/org/service.ts`: no future dates, nothing before the current assignment began, manager must be active, no loops. It writes history.
- Loops are refused by a database trigger (advisory-locked, so concurrent changes cannot slip past). Never update `manager_id` outside `applyReporting`.
- **"Team" scope = everyone below you in the chain** (direct and indirect). Resources for team checks carry `managerChainUserIds` (see `managerChainUserIds()`); without it team access is denied. A manager sees a report's profile in a **limited view**: no birth date, civil status, personal email or home address.
- A person who still has active reports cannot be archived or marked separated; HR reassigns them first (`reassignReports`).
- Positions are a catalog; `employees.position` is the display title kept in sync.
- To roll back a half-finished multi-step action, **throw** `ActionFailure` inside the transaction (returning commits).

## Files, notifications and background jobs

- **Files:** private buckets `employee-docs` and `company-docs` (create them with `pnpm storage:setup`, local or hosted). Upload is three steps: `requestUpload` (validates, server picks the path, returns a one-time token) -> browser uploads straight to storage -> `finalizeUpload` (server reads the file, checks the real type by its bytes, size and SHA-256, then activates it; a failing file is deleted). Never trust the browser's file name or declared type. Downloads are 60-second signed links and every one is audited. Archiving keeps the file until retention periods are approved.
- All storage goes through `DocumentStorage` (`src/modules/documents/storage.ts`); tests use `FakeStorage`. Do not call Supabase Storage from anywhere else.
- **Every exported function in a "use server" file is a public endpoint.** Each must call `requireUser()` first, and helpers that take the acting user as a parameter belong in a separate server-only file (see `service.ts` files). `tests/authz/server-actions-guard.test.ts` enforces this.
- **Notifications:** `notify()` (`src/modules/notifications/service.ts`) writes in-app notifications; links must be relative. The bell in the header reads only the signed-in person's own.
- **Jobs (Inngest):** scheduled functions in `src/inngest/functions.ts` are thin wrappers around plain tested functions (`src/modules/documents/jobs.ts`). Local: `INNGEST_DEV=1` in `.env.local` plus `pnpm dlx inngest-cli@latest dev`. Production: `INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY`; without a key the endpoint refuses to run. Job dates follow the company time zone (`America/Phoenix`).

## Announcements, policies and email (Phase 1.4)

- `src/modules/announcements/`: announcements (Markdown, audience everyone or teams, recipients frozen at posting), versioned policies (`docs.policy_versions`: a published version is frozen by a database trigger; changes are new versions), and `docs.acknowledgments` (insert-only trigger; one row per person and item/version). For policies the `id` in actions is the policy **version** id.
- Markdown goes through `src/lib/markdown.ts` into React elements, never an HTML string. Do not add `dangerouslySetInnerHTML` for user text.
- The seeded privacy notice and monitoring policy are DRAFT placeholders; publishing refuses text containing "DRAFT PLACEHOLDER". Phase 1.5 and the Jibble mirror gate read them by `kind`.
- **Email:** everything is queued in `ops.email_queue` and sent by the `email-sender` job under a rolling 24-hour budget (`EMAIL_DAILY_BUDGET`, default 90 of Resend's free 100). Acknowledgment emails go first, then the weekday 8:00 AM Manila digest. Bodies carry counts and a link only. With no `RESEND_API_KEY`/`EMAIL_FROM` nothing is sent and the queue waits. Tests use `setEmailSender()`.
- Pass `Date` values to drizzle comparison helpers (`lt`, `gte`), not raw `sql` fragments: raw fragments skip the driver's date encoding.
- Production go-live: Supabase's built-in auth email is heavily rate-limited; configure custom SMTP (Resend can do it) when the Pro project is created.

## Privacy notice and "My data" (Phase 1.5)

- **Gate:** `(app)/layout.tsx` calls `getPrivacyGate()` (`src/modules/privacy/queries.ts`). Until the current published version of the policy with `kind = 'privacy_notice'` is accepted, the layout renders only the acceptance screen. No published notice = no gate; a failure loading it fails open. It is a page-level gate; actions still authorize normally. Acceptance is the same insert-only `docs.acknowledgments` row as any policy (accounts with no people record may accept it too). The privacy notice and monitoring policy always get `requires_ack = true` when published.
- **Publishing the privacy notice is permanent** in a database (versions are frozen), and it stops everyone at the screen. Never publish one against a shared dev database you still use for e2e: `tests/e2e/privacy-gate.spec.ts` runs in its own Playwright project after the others and archives the policy at the end (`update docs.policies set archived_at = now()` switches the gate off). If that test crashes, run that SQL.
- **My data** (`/my-data`): `collectMyData()` in `privacy/service.ts` reads only the signed-in account's own rows, returns sensitive fields as stored masks (never decrypts), and names no other person in the activity list. JSON and PDF (`pdf-lib`, Helvetica, non-Latin text becomes "?") come from `exportMyData`, rate-limited and audited as `mydata.export`.
- **Data rights requests** reuse `core.change_requests` with category `data_rights` (correct, delete, other). HR is notified; approving applies nothing automatically, because deletion is a retention and counsel decision.
- After adding a migration, run `pnpm db:migrate` against the local database before `pnpm test:e2e`: the integration tests build their own database, so they will not reveal a missing local migration.

## Time off: prize days and holidays (Phase 2.1)

- ERS engages 1099 contractors, so there is **no accrual, policy table, carry-over or eligibility rule**. Days off exist only as **prize days** HR awards (`awardDays`, max 5 per award, whole or half days, reason required, optional "use by" date). UI copy says "prize days off", never "PTO" or "paid time off". If ERS ever adds paid leave, add policies and an accrual job on top of the same ledger.
- `time.leave_ledger` (`src/modules/timeoff/`) is append-only (trigger). Entry types: award, usage, reversal, adjustment, expiry, opening_balance; `days` is signed and checked per type. Balance = sum of rows, never stored. Writes for one person take `lockEmployeeLedger()` (advisory lock) so balance checks cannot race. Nobody awards or adjusts their own days (another admin must). Balances never go below zero.
- **Expiry** (`runLeaveExpiry`, daily 1:15 AM Phoenix): writes an `expiry` row (unique per award, so it is idempotent) for what was left unused. What is "left" comes from the pure replay in `ledger.ts`: usage draws from the days that expire soonest first, expired days cannot be drawn, a reversal gives back the most recent draws. Phase 2.2's request flow must write `usage`/`reversal` rows with `effective_on` set to the leave date and use the same lock.
- **Holidays** (`time.holidays`, calendars PH and US, seeded for 2026 and 2027): US federal dates are marked verified; Philippine dates start unverified because each year's list is proclaimed by the government (HR checks them and ticks "verified"). `core.clients.holiday_calendar` picks a client's calendar; a person sees the Philippines plus their current clients' calendars.
- A CHECK constraint passes when it evaluates to NULL: wrap nullable columns in `coalesce` (this bit `leave_ledger_reason_chk`).

## Time off requests and approvals (Phase 2.2)

- `time.leave_requests`: pending_lead -> pending_hr -> approved, or declined / cancelled. The lead step is decided by anyone above the person in the chain (`timeoff.approve` team scope); HR (`timeoff.approve_final`) decides the last step, may only **decline** (not approve) at the lead step, and a lead step that waits 4 working days is escalated to HR by the daily job. A leave type with `skip_hr` finishes at the lead. Nobody decides their own request or one they filed. Nobody above the person = HR decides alone.
- **Days** are working days (Monday to Friday minus PH and client holidays) until schedules exist in 2.5; `workdays.ts` is the one place that rule lives. Requests cannot start in the past (HR files those, `timeoff.file_for_others`), prize-day types need 1 working day's notice, and two live requests for the same person may not overlap (a Postgres exclusion constraint, needs `btree_gist`).
- **Ledger:** approval writes one `usage` row (effective on the first day, tagged with the request id) after `canTake()` passes inside the ledger lock; cancelling approved leave writes a `reversal` dated no earlier than the usage, tagged with the same request id so the replay returns exactly that request's days. Days cannot be used before they were awarded or after they expire.
- **Invites:** approval and cancellation queue an email of kind `invite` with an .ics attachment (`ics.ts`, all-day, title "Day off", no leave type). Email attachments are stored in `ops.email_queue.attachment` and sent through Resend.
- **Calendar** (`getTeamCalendar`): HR sees everyone with leave types and pending requests; a Team Lead their downline; an Executive only counts per day; everyone else their teammates by name (approved only, leave type hidden except their own).
- E2E tip: in the dev server a page can load before React hydrates, and text typed into a controlled field before then is lost. Use `waitForHydration(page, selector)` from `tests/e2e/helpers.ts` before filling forms.

## The time clock (Phase 2.3)

- `time.clock_events` (`src/modules/attendance/`) is append-only (trigger). Web events get the **database clock** (`clock_timestamp()`) and the IP from `x-forwarded-for`; nothing the browser sends can change either. `performClock()` (service.ts) does everything inside `lockEmployeeClock()`: state machine from `clock.ts` (out -> working <-> break -> out; a clock-out on a break writes `break_end` first), no clock-in on approved full-day leave, IP range flag, location, selfie.
- **Breaks are unpaid** (deducted from worked time). The **calendar day** of a session is the day it STARTED in the person's own zone (`time.clock_prefs.time_zone`, default company zone), so a night shift is one day. `attendance_days` is rebuilt nightly from events (`rebuildAttendanceDays`), never hand-edited; the My time page computes live from events.
- **Allowed IP ranges are per team** (`time.clock_rules`): outside = flagged for the lead, never blocked; no row = no restriction. IPv4 and CIDR only.
- **Location and selfie are monitoring**: both work only while a policy with `kind = 'monitoring'` is published (`monitoringPolicyPublished()`), location also needs the person's opt-in (stored rounded to 2 decimals, about 1 km), selfie needs the team rule. Selfies live in `employee-docs/selfies/<employeeId>/`, are checked by their bytes (JPEG, 1.5 MB), and are deleted after 30 days (`purgeSelfies`); the row stays.
- **Idle prompt** only flags (`time.idle_prompts`), it never clocks anyone out. **Missed clock-out**: a session open over 12 hours notifies the person and their lead once (schedule-based grace comes with Phase 2.5).
- **Corrections** are requests (`time.clock_corrections`) approved by the lead (HR for anyone); approval writes NEW `admin_correction` rows and re-checks that the proposed events fit and break nothing that was valid. Nobody decides their own.
- **Timed breaks:** a break can be 15, 30 or 60 minutes or open-ended (`planned_break_minutes` on the `break_start` event; only those lengths are accepted). A timed break past its length plus a one-minute grace is an **overbreak**: the person sees a "Your break is up" pop-up in the header, the minutes show on the timesheet (`overbreak` flag and `attendance_days.overbreak_minutes`), and the lead (HR when nobody is above) is notified once per break (`time.overbreak_notices`), either when the break ends or by the 5-minute `runOverbreakAlerts` job while it is still running. An overbreak on a finished break counts even while the session is open.
- **Every clock-in is its own record**: `buildDays()` keeps `sessionList` for each day and the My time table shows each session under its day; days are only summed, never merged away.
- **Internal staff use the clock too**: it needs a people record, so HR and Super Admin accounts without one see "Set up your time clock" in the header and can create or link their own with `createMyProfile` (links an unlinked record with the same email first; audited). Anyone else asks HR to add them.
- `performClock()` hands each clock event to `enqueueMirror()` (Jibble link, Phase 2.4) inside the same transaction.
- Tests that need a published monitoring policy use `withMonitoring()` in `tests/integration/attendance.test.ts` (adds a published version, then archives the policy), so the seeded placeholder (version 1) stays intact for the announcements tests.

## Clock reliability, time claims and end-of-day notes (Phase 2.3.1)

- **Offline:** the clock is online-only on purpose (rule 9: the server owns the time). The header widget shows "Offline: clock paused" and disables the buttons; a failed request says nothing was recorded. There is no offline queue: a missed moment is fixed with a time claim.
- **Heartbeat:** a clocked-in page calls `pingPresence` every 2 minutes (and when the tab becomes visible). It stores only the latest time per person in `time.clock_presence` (no history), set at clock-in too. The reply carries the PREVIOUS time seen, so a gap over 15 minutes shows "Welcome back": "Yes" or "I stopped at ..." (a clock-out correction, kind connection_problem, device_problem or forgot). Never discard a ping reply: the ping itself counts as seen. Leads see "Last seen" and "Possibly offline" (10 minutes without a ping; display only, nobody is clocked out). `runQuietSessionAlerts` (every 15 minutes) tells the lead once when someone working has not been seen for 2 hours (`time.quiet_notices`). The 12-hour missed clock-out notice stays.
- **A waiting clock-out request** (`pendingClockOut`) blocks other clock actions for that person until it is decided or cancelled.
- **Time claims = corrections with proof** (`time.clock_corrections` has `kind` and `original_proposed`; screenshots in `time.correction_evidence`, files in `employee-docs/time-evidence/<employeeId>/`). A claim that adds a clock-in needs 1-3 JPG/PNG screenshots (5 MB, bytes checked, SHA-256 stored); upload goes through `requestEvidenceUpload` then the claim attaches them. Screenshots support the reviewer; they are never hours. Only the person, their chain of leads and HR open them (60-second signed link, audited as `clock.evidence_view`). Files are deleted 90 days after the decision, unattached ones after a day (`purgeEvidence`). Upload screens warn: never include client or patient information.
- **Who decides:** the lead (HR when nobody is above). HR only when it was filed for the person by someone else or reaches back more than 7 days from when it was filed (`needsHrDecision`). Nobody decides their own or one they filed. The reviewer may change the times when approving (kept in `original_proposed`, the person is told).
- **File for others** (`fileCorrectionForOthers`, `attendance.file_for_others`: HR anyone, lead their downline): notifies the person and HR; HR decides.
- **End-of-day notes** (`time.shift_notes`, one per session keyed by its clock-in event id, plain text up to 5,000 characters): optional box after clock-out (`ClockResult.sessionId`), editable by the author for 24 hours after clock-out (`edited` is set), visible to the author, the chain of leads and HR (`attendance.notes_view`). A team rule `eod_expected` only adds a `no_eod` flag to the nightly rebuild; it never blocks clock-out.
- E2E: after any clock-out the "Wrap up your day" box opens; click "Skip" before the next step.

## The Jibble link (Phase 2.4)

- **Jibble is only for screenshots.** ELEVATE is the time clock and the only source of hours. Never store Jibble screenshots, GPS or activity; the only thing read back is tracked-minute totals for the nightly comparison (`time.jibble_daily`, kept 35 days, never used for hours or exports).
- **Credentials:** a personal access token (`JIBBLE_ACCESS_TOKEN`, works on Jibble's free plan and acts as the person who made it) or a Client ID + Secret. Local tests use the git-ignored `apps/elevate/.env.jibble.local`; production uses the host's environment. No token = nothing is sent and the clock works as usual. A rejected token (401/403) alerts HR once a day. Never log tokens; failures store only a short code and the HTTP status (`describeFailure`).
- **Code:** `src/modules/jibble/`. `http-client.ts` is plain fetch (no server-only, so `pnpm jibble:probe` can use it): Workspace `/v1/People`, TimeTracking `POST /v1/TimeEntries` (type In, Out or StartBreak) and `/v1/TimeEntries/EndBreak`, TimeAttendance `/v2/TimesheetsSummary`. `client.ts` holds the configured client and `setJibbleClient()` for tests (use a fake in every test; never call the real API from tests). `mirror-rules.ts` is the pure part.
- **Mirror (outbox):** `enqueueMirror()` writes `time.jibble_link_log` rows (one per clock event) in the clock transaction when ALL are true: a client is configured, `JIBBLE_MIRROR_ENABLED` is not `false`, the monitoring policy is published, and the person's team has `clock_rules.jibble_mirror` on (HR sets it in the Rules tab; turning it on needs the published policy). `processMirrorQueue()` sends them (Inngest event `jibble/mirror.requested` plus a 5-minute sweep), one person at a time in click order; network trouble, 429 and 5xx retry 6 times over about an hour, a refusal is final, 409 counts as sent, a retrying call holds later calls for that person. A person with no Jibble match gets a `skipped` row. Jibble being down never blocks or slows the ELEVATE clock.
- **Breaks:** `JIBBLE_BREAK_MODE` = `native` (the default: Jibble's own breaks), `clock` (break start sends Out, break end sends In) or `off`. Native mode needs **breaks set up in Jibble** (Settings > Breaks, available through each person's schedule; make them Unpaid, since ELEVATE's breaks are deducted). Jibble lists breaks **per person** (`GET /v1/GetBreaks(personId,time)`; the plain `/v1/Break` list is something else), so a break start reads the person's breaks (cached 10 minutes) and `pickBreak` chooses: unpaid first, exact length, else a flexible one (length 0 = "staggered", fits any length), else the shortest long enough, else the longest, and sends its `breakId`; a break end (`/v1/TimeEntries/EndBreak`) points at the entry that started it. With no break available to the person, StartBreak fails (not retried) and HR sees it in the Jibble page; "Test connection" warns. A clock-out on a break sends only Out in clock mode and EndBreak then Out in native mode. Corrections are never mirrored.
- **Fallback mode** (`JIBBLE_MIRROR_ENABLED=false`): ELEVATE sends nothing, people clock into both apps, and the nightly comparison finds gaps.
- **People:** `time.jibble_people` (own table, not a column on employees) matched by work email nightly (`syncJibblePeople`) or by hand in the Jibble page; a hand-made match is never overwritten and one Jibble account is never given to two people.
- **Nightly comparison** (`runJibbleComparison`, 3:10 AM Phoenix, after the 2:30 rebuild): for people on teams with the switch on, yesterday in the person's own zone; ELEVATE minutes = worked minutes (plus break minutes when breaks are not sent); more than `JIBBLE_MISMATCH_MINUTES` (default 15) apart sets the `jibble_mismatch` day flag (also on a day with no ELEVATE record). The nightly rebuild keeps the flag.
- **HR tab:** Attendance > Jibble (`jibble.manage`, HR and Super Admin only): connection test, match people, recent calls with Retry.
- `pnpm jibble:probe [email] [--clock] [--native-break]` checks the token and tries one TEST person; use it before turning a team on to see whether an API clock-in really starts the desktop app's screenshots.

## Schedules and flags (Phase 2.5, part A)

- **Schedules** (`time.schedules`, `src/modules/attendance/schedule.ts` is the pure part): a dated shift pattern per person: start and end (HH:mm in the schedule's zone, usually the client's; an end at or before the start ends next day), ISO working weekdays (1 = Monday), a planned unpaid break, effective dates. A new schedule closes the old one the day before; the past is not edited; two schedules for one person cannot overlap (exclusion constraint). HR and Super Admin set them (`assignSchedule` for one or many, all or nothing; start no more than 7 days back); leads and people read them. Everyone sees them in the schedule's zone, their own and Manila.
- **A shift belongs to the day it STARTS in the person's own zone** (`shiftOn()`), the same rule as attendance days, so a US-hours shift worked from Manila is one day. Daylight saving moves Manila hours, never the client's.
- **Nightly flags** (`rebuildAttendanceDays`, columns `scheduled_minutes`, `late_minutes`, `early_leave_minutes`, `extra_minutes`): `late` and `left_early` past the team's `late_grace_minutes` (default 10); `extra_hours` = worked minus scheduled, ignoring under 15 minutes (a shifted day is not extra); `rest_day_work` and `holiday_work` count in full as extra; `absent` = a scheduled day that ended with no clocking, no approved leave and no holiday (the flag is taken off again if events or leave appear). **People with no schedule get none of these.** Holidays are the person's PH plus their clients' calendars.
- **Missed clock-out** now fires at shift end plus the team's `grace_minutes` (default 60), once per session (`missed_clockout_notices`); the 12-hour rule remains the backstop for people with no schedule.
- **Leave days** use the person's working weekdays in their own zone when they have a schedule (`workingWeekdaysFor`), Monday to Friday otherwise (`workdays.ts` takes an optional weekday set).
- **Schedules page** (`/schedules`, its own menu item): everyone sees their own schedule (`getMySchedule`: current, next, earlier); HR also gets the assign form and everyone's list (`SchedulesPanel`); a Team Lead gets a read-only list of their team (`listTeamSchedules`). The Attendance My time page shows a one-line schedule with a link here. E2E: the My time table has Shift and Extra columns.

## Extra hours (Phase 2.5, part B)

- UI and copy say **"extra hours"**, never "overtime" (1099 contractors; counsel to confirm wording). ELEVATE labels hours and never computes pay.
- **Requests** (`time.extra_hours_requests`, `extra-hours-actions.ts`): a window of time for a client the person is assigned to. **VA asks** (`requestExtraHours`): needs 1-3 screenshots of the client's approval (the same private upload and checks as time claims, `correction_evidence.extra_request_id`, `requestExtraEvidenceUpload`), a client contact name (free text) and a reason; status `pending_lead`. **Client asks** (`fileExtraHoursFor`, lead for their team or HR for anyone): proof, or "confirmed by phone" with a reason; status `pending_confirm`; the VA confirms (approved, decided by the filer) or declines (`answerExtraHours`). The filer is the approver. Evidence is bound to who uploaded it (`uploaded_by`).
- **Decision** (`decideExtraHours`): the person's lead, HR when nobody is above. HR only when it was asked for **after the fact** (the window had started) and more than 7 days before it was filed. Nobody decides their own request or one they filed. The reviewer may change the window when approving (kept in `original_window_*`). Cancel (`cancelExtraHours`): the person or filer while it waits; the lead or HR also for approved time that has not started.
- **Limits** per team (`clock_rules`): `max_extra_minutes_per_day` (240) counts pending and approved requests together; `max_day_minutes` (720) only warns. A request is 15 minutes to 24 hours, up to 30 days ahead and 31 days back. Two live requests for one person cannot overlap (exclusion constraint). Pure rules: `extra-hours.ts`.
- **Effect on hours** (nothing blocks the clock): a day's extra time (see schedules) is split into **approved** (up to the minutes granted by that day's approved requests, by the day each window STARTS in the person's own zone) and **unapproved** (what is left, if 15 minutes or more): `attendance_days.approved_extra_minutes`, flag `unapproved_extra`. Approved windows that run on from the shift end push the missed clock-out time back.
- **Header** (`ClockStatus.shiftEndMs`, `extraWindows`): 5 minutes after the shift end with no approved window, a "Your shift has ended" prompt (ask for extra hours, clock out, or dismiss); 5 minutes before an approved window ends, a reminder. Neither clocks anyone out.
- **Jobs:** `runExtraHoursReminders` (every 30 minutes, once per request: a request still waiting when its window starts within 2 hours goes to the lead again and to HR; a client's request waits on the VA and the filer); `runWeeklyExtraHoursNotice` (Monday 8:00 Manila, in-app to HR: last week's approved extra hours per client, by when each window started).
- **Extra hours page** (everyone): your requests and the form; leads and HR also see the review queue and the "file for the client" form.

## Hours review, approval and export (Phase 2.5, part C)

- **Review** (Attendance > Review, `hours.approve`: a lead for their team, HR for everyone; `hours-queries.ts`): a week per person from `attendance_days` (scheduled, worked, extra approved and not, flags) with approval state. Defaults to last week.
- **Approval** (`approveHoursWeek`, `approveCleanWeeks`; the logic is `approvePersonWeek` in `hours-approve.ts`): approves the FINISHED days (before today in the person's own zone) of a Monday-to-Sunday week, up to 5 weeks back. It first rebuilds that person's days from the clock events (`rebuildAttendanceDays(now, daysBack, employeeId)`) so the numbers are current, refuses while a session from that week is still open, and never lets anyone approve their own hours. **`time.hours_approvals` is append-only (trigger)** and stores the numbers approved (scheduled, worked, break, extra, approved extra); the newest row per person and day is current. A day whose current numbers differ from its approval is **"changed after approval"** and must be approved again (a new row). Approving the same numbers twice stores nothing. "Approve everyone without flags" skips anyone with a flag outside `CLEAN_FLAGS` (on_leave, corrected, extra_hours).
- **Export** (Attendance > Hours export, `hours.export`, HR only; `hours-export.ts`, `exportHours` returns the CSV text and the browser saves it; audited as `hours.export`, rate-limited, cells go through `csvCell` so names cannot run as formulas): per pay period, the **daily detail** (shift, scheduled, first in, last out, breaks, worked, regular, approved and not-approved extra hours, late and early minutes, flags, approval, approver) or a **per-person summary** (totals, absent and late days, approved leave days). Only days whose numbers equal their latest approval are included; "include days not approved" adds the rest, labelled "Not approved" or "Changed after approval". ELEVATE totals and labels hours only; it never computes pay and never reads hours from Jibble.
- **Pay periods** (`pay-periods.ts`, `time.hours_settings`, one row): semi-monthly (1st-15th and 16th-end) by default, or weekly, every two weeks (from an anchor Monday) or monthly. HR changes it on the export tab.
- E2E: seed `attendance_days` rows directly (the nightly rebuild would have written them); approval itself rebuilds from events.

## Hardening before the pilot (Phase 2.6, part 1)

- **Safety lock** (`sendsAllowed()` in `jibble/client.ts`): ELEVATE sends to Jibble only when `ELEVATE_ENV=production`. Anywhere else (laptops, staging, tests) it sends only for Jibble person ids in `JIBBLE_TEST_PERSON_IDS`; other calls are logged as skipped ("not sent: not the production environment"). The live Jibble organization is real people: **set `ELEVATE_ENV=production` only on the production deployment**, and tests that need sending set it themselves.
- **Repair job** (`runJibbleRepair`, every 10 minutes): for people on teams that use Jibble who are working or clocked out in the last 30 minutes, compare ELEVATE's state with Jibble's latest time entry (`latestState`) and send the call that fixes the difference (`repairAction`: ELEVATE is the source of truth). It skips people with a waiting call, a click in the last 3 minutes, a repair in the last 9 minutes, and does nothing while paused; at most 150 people a run. Repair calls are `jibble_link_log` rows with `source = 'repair'` and no event. A **retry first checks Jibble's state** so a call that went through is not sent twice.
- **Break fallback:** a native break start that Jibble refuses (no break for the person, already used; not auth, not a retryable error) sends a clock-out instead (`fallback = true` on the row) so screenshots still stop; its break end then sends a clock-in.
- **Pause switch** (`time.jibble_settings`, `setJibblePaused`, HR): while paused nothing is sent and calls wait. On resume, calls that waited more than 10 minutes are dropped (replaying a backlog would put Jibble in a wrong state) and the repair job sets Jibble right.
- **Alerts:** auth failures alert HR at most every 2 hours (`jibble.auth`); 3 or more failed calls in 2 hours alert at most every 6 hours (`jibble.failing`); the Jibble page shows a banner when the oldest waiting call is 15 minutes old. A 429 waits at least its `Retry-After`. One token request at a time per server. **Unmatched people** (`runJibbleUnmatchedReport`, daily): HR gets one list of who clocked in with no Jibble account yesterday; the day gets the `no_screenshots` flag (not for the safety-lock skip).
- **The clock never depends on the rate limiter:** `clock` and `presence` fail open when Upstash is missing or unreachable (`allowWhenLimiterUnavailable`); every other policy still fails closed in production. The header says "Cannot reach ELEVATE: refresh, or sign in again" when the browser is online but requests fail.
- **Payroll completeness:** every Monday 8 AM Manila each lead is told how many of their people have unapproved hours from last week (HR for people with no lead); Wednesdays HR gets who is holding it up. The Hours export tab shows approved versus not approved days by team for the latest periods, and an export tells HR how many finished days it left out. "Absent" is labelled "Absent (review)": never an automatic deduction.

## System health, bulk corrections and the runbook (Phase 2.6, part 2)

- **Health** (`src/modules/health/`, Attendance > Health, `health.view`, HR and Super Admin): every scheduled function in `src/inngest/functions.ts` is wrapped in `track("<id>", ...)` (`trackJob`), which checks in to `ops.job_runs` (job, start, last success, last error CLASS NAME only, run count). `registry.ts` lists every job and how often it should succeed (`JOBS`); a job that has not succeeded for 2.5 times that plus 5 minutes is "late". A test checks that every function is in `JOBS` and tracked, so **a new scheduled job must be added to both**. `runHealthCheck` (every 30 minutes) tells HR once every 6 hours (`system.health`) about late jobs or a Jibble call waiting 15 minutes or more (not while paused). The page also shows the Jibble queue and clock activity.
- **Backstop:** `/api/cron/backstop` (called by the host's scheduler every 15 minutes, `vercel.json`) runs the health check, `processMirrorQueue`, `runJibbleRepair` and `runMissedClockouts`, so attendance-critical work and the health alert survive the job service being down. It is outside the sign-in gate (all `/api` routes are) and checks `CRON_SECRET` itself (`cronAuthorized`, constant time, at least 16 characters; no secret = nobody gets in). It does not check in as the jobs (that would hide a job-service outage).
- **Bulk corrections** (`fileBulkCorrections`, `decideCorrectionBatch`, `bulk-corrections.ts`; HR only, Attendance > Corrections): a CSV of `email,type,time` (times in a zone HR picks, up to 500 rows, up to 6 events per person) becomes one ordinary correction request per person with the same `checkProposal` checks, sharing a `batch_id`. Rows that cannot be filed are returned with the reason. **Another HR admin** decides the whole batch (each request is decided by the normal `decideCorrection`, so the filer can never decide, and each is re-checked); one notification goes to the other HR admins, one to each person.
- **Runbook:** `docs/RUNBOOK.md` is the plain-language guide for outages, sign-in recovery (MFA reset is done in the Supabase dashboard; there is no in-app reset), Jibble problems, deploying at the Manila shift change, and the pilot checklist. Keep it current when behavior changes.

## Recruiting (Phase 3.1)

- `src/modules/recruiting/`, schema `talent`. **Applicants are not employees**: `talent.candidates` (one per email, case-insensitive), `applications` (one per candidate and job), stage history, notes, interviews, interviewers, scorecards, applicant emails, one-row settings. Stages are fixed (`constants.ts`): applied, screening, interview, assessment, offer, hired, rejected. Rejected has a `close_kind` (rejected or withdrawn). A hire is final; a rejected application is reopened by moving it to a stage. **"Hired" only marks the application**: creating the person record and onboarding come with offers (3.3).
- **Public pages** (no sign-in, indexable): `/careers` (open jobs only) and `/careers/[id]` with the apply form. The form posts to `/api/careers/apply` (a route handler, not a server action): Upstash rate limit `careers` (5 an hour per address, fails closed in production), honeypot field `website` (a filled one gets the same "ok" and stores nothing), privacy consent required (the published privacy notice version is stored with the candidate), resume PDF or DOCX up to **4 MB** (Vercel's body limit; checked by its bytes, SHA-256 stored) written by the server to the private bucket `recruiting-docs` (`pnpm storage:setup`). Applying twice to the same job looks the same to the applicant and adds nothing; applying to a second job replaces the resume with the newest file. Public pages say "contractor", never promise pay or benefits (the pay note is free text). No fields for client or patient information anywhere.
- **Access:** `recruiting.view` and `recruiting.download_resume` are "all" for HR, Super Admin and recruiters, and "team" for a team lead, where the resource's chain is **that opening's hiring team** (`authorizeForOpening`, `openingHiringTeam`). Only HR, Super Admin and recruiters create jobs, move and close applications and schedule interviews. The Executive gets counts only (`recruiting.summary`). `NavItem.access` hides the Recruiting item from roles with none of these; the page 404s for them.
- **Board** (`/recruiting/[id]`): drag a card or use its "Move to" menu (**dnd-kit** `@dnd-kit/core`: drag by the grip with a mouse, a finger (150 ms press so scrolling still works) or the keyboard: space, left and right arrows jump a column, space; the "Move to" menu is the fallback). Each applicant has a page (`/recruiting/applications/[id]`) with details, resume (60-second signed link, audited as `recruiting.resume_view`), stage controls, notes, interviews, scorecards and history. Every move writes `talent.application_stage_history` (**append-only trigger**) and an audit row.
- **Interviews** are scheduled with a time, length, place or link and one or more interviewers (HR, Super Admin, recruiters, team leads). Interviewers get an `.ics` invite through the normal email queue (kind `invite`, no applicant name in the email) and a notification; the applicant gets the invite by the applicant email queue if the recruiter leaves the box ticked. Cancelling sends a cancellation. Interviews can also be created on Google Calendar (below).
- **Google Calendar for interviews** (Phase 3.1b, `google.ts`, `calendar.ts`): HR, Super Admin and recruiters connect **their own** calendar (Recruiting page card; `/api/google/connect` then `/api/google/callback`, with a one-time `state` cookie checked in constant time, and the MFA session re-checked). Scope `calendar.events` plus `openid email`. The refresh token is stored in `talent.calendar_connections` **encrypted with the field-encryption key bound to the user** (`google_calendar:<userId>`); access tokens are never stored. Add the `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (a separate client from Supabase sign-in, `docs/SETUP.md` 6b); with none, the card says it is not set up and everything uses `.ics`. `scheduleInterview` first creates the event on the **scheduler's own** calendar (event id derived from the interview id, so a retry cannot duplicate it; Meet link requested; guests are the interviewers' sign-in emails and, if ticked, the applicant; the title names the job, never the applicant) and stores `calendar_mode = 'google'`, `google_event_id`, `meet_link`, `calendar_user_id`; **ELEVATE then sends no .ics** for that interview (Google invites), though interviewers still get the in-app notification. If the scheduler is not connected, or Google fails or refuses, the interview falls back to the `.ics` emails with a warning, and **scheduling never fails because of Google**. An `invalid_grant`/401 marks the connection `needs_reconnect` (Testing-mode External apps expire tokens after 7 days; Internal or published apps do not). If saving the interview fails after the event was created, the event is deleted. Cancelling deletes the event with the organizer's connection (any HR admin can cancel); if that fails the interview is still cancelled and the screen says to delete the Google event by hand. Tests use `setGoogleClient(fake)`; **never call Google from tests**. Rotating `FIELD_ENCRYPTION_KEYS` does not re-encrypt these tokens: keep the old key until people reconnect, or extend the re-encrypt job.
- **Scorecards** (`talent.scorecards`, **append-only**, one per interviewer per interview, only after the interview has started, never editable): four ratings 1 to 5, a recommendation and a reason. An interviewer sees the others' scorecards only after submitting their own; HR, Super Admin and recruiters who are not interviewers on that interview see all.

Sign-up confirmation and password-reset mails come from **Supabase Auth**, not from this sender (local: Mailpit at :54324; production: custom SMTP).
- **Applicant emails** (`talent.candidate_emails`, job `candidate-email-sender` every 10 minutes, own cap `CANDIDATE_EMAIL_DAILY_BUDGET`, default 20): "received" (per-job switch), rejection (only when the recruiter ticks it, and the job allows it) and interview invites. They never contain scores, notes or reasons. `EMAIL_APPLICANT_BCC` (optional) adds a silent copy of each to a shared mailbox such as talent acquisition's. With no `RESEND_API_KEY` they wait in the queue.
- **Retention** (`runRecruitingRetention`, daily 3:30 AM Phoenix, job `recruiting-retention`): **off until HR switches it on** (Recruiting page, `recruiting.manage_retention`); the periods default to **12 months after a rejection and 6 after a withdrawal and need counsel's approval**. When every application of a candidate has been closed longer than its period (never for a hired person or anyone with a live application), the candidate row is anonymized (name, email, phone, country, resume file removed), notes and applicant emails deleted, scorecard free text replaced with "[removed]", application notes cleared; counts and stage history stay. The append-only triggers allow this only inside a transaction that sets `talent.retention = 'on'` (set by that job alone).

## ELEVATE Sign (Phase 3.2)

- `src/modules/signing/`, tables `docs.esign_templates`, `esign_envelopes`, `esign_signers`, `esign_events`; files in the private bucket **`signed-docs`** (`pnpm storage:setup`). The menu item is **Signing** (`/signing`: To sign, All documents and Templates for HR; `/signing/new`; `/signing/[id]`). The public **`/verify`** page and its route `/api/signing/verify` need no sign-in.
- **Flow:** HR uploads an 8 MB, 100-page PDF (or picks a template) and the signers, in order or all at once (`createEnvelope()` in `service.ts` is the one entry point; **offers (3.3) and onboarding (3.4) call it**). Creation goes through route handlers `/api/signing/envelopes` and `/api/signing/templates` (large files; `requireUser()` and `authorize()` first, rate limit `upload`). **Signers must have an ELEVATE account** (they sign while signed in at AAL2). People outside the company (a candidate with an offer) sign as **outside signers** (see Offers and hiring).
- **Signing rules** (`actions.ts`): a signer must have **opened the document** (recorded as a `viewed` event), tick the consent (`CONSENT_TEXT`, version stored), then type (Latin-1 letters only, drawn in a standard italic font) or draw (a PNG up to 60 KB and 1000x400, checked by its bytes) their signature. Sequential order wakes the next signer(s) (`signersToActivate`); a decline ends the envelope (others cancelled, HR told); HR can void before everyone has signed; envelopes expire after 14 days by default; reminders every 3 days. IP comes from the request and the sign-in methods (e.g. "password, totp") from the auth server (`session.ts`), never from the browser. Emails to signers carry no titles or names.
- **Sealing** (`sealEnvelope`, `seal.ts` pure): reads the original, checks it still matches its SHA-256, adds a **signature page** (signatures are not placed on the original pages) and a **certificate** (document, reference `ES-XXXXXXXX`, signers with UTC, Manila and Arizona times, IP, how they signed in, event log), stores the sealed copy and its SHA-256 and completes the envelope. It runs after the last signature; if it fails the signature stands and the 5-minute **`esign-seal-sweep`** job finishes it (safe to repeat). Daily **`esign-reminders`** expires and reminds. Both are in the health registry.
- **Evidence is immutable** (triggers in migration 0030): `esign_events` is append-only and **hash-chained** (`chain.ts`; HR sees "Chain intact" or "broken" on the page), a signed signer row never changes, a sent envelope's original and a sealed copy cannot change, a finished envelope's status is final, and only a draft can be deleted (a discarded draft is voided, keeping its log). Originals are kept even for discarded drafts. **Retention of signed documents is not automated** (counsel to decide); nothing deletes them.
- **Documents are viewed in the page, not downloaded:** `DocumentViewer` (`src/components/document-viewer.tsx`) shows a PDF in an iframe from our own authenticated route (`/api/signing/[id]/document`, `/api/recruiting/resume/[applicationId]`), which runs the same checks as the download link (`openSigningDocument`, `openResume`), audits the view and answers `Content-Disposition: inline`, `no-store`. It is served by the app, not by storage, because Supabase storage links are sandboxed and a browser's PDF viewer will not show them in a frame. Download is a separate button (60-second signed link, `download` set). A signer's first open (viewer or download) is what unlocks signing. **A Word resume cannot be shown by a browser**: those only offer Download. Any new place that shows a stored PDF should reuse this pattern.
- **Verify** hashes the PDF in the browser and sends only the fingerprint (rate limit `verify`): the answer is match or no match, the seal date and the reference, nothing about who signed. A one-byte change fails.
- Wording says "agreement" and "signature" (1099 contractors); the consent text and RA 8792 fit should be reviewed by counsel. Notarized documents still need wet ink.
- Tests: `src/modules/signing/signing.test.ts` (pure), `tests/integration/signing.test.ts`, `tests/authz/signing-actions.test.ts`, `tests/e2e/signing.spec.ts`.

## Offers and hiring (Phase 3.3)

- `src/modules/offers/`, tables `talent.offer_templates`, `offers`, `onboarding_cases`. **Templates** (HR, `/recruiting/offer-templates`) are Markdown-style letters with fixed `{{merge_fields}}` (`merge.ts`: candidate_name, offer_date, expires_on, role_title, start_date, client_name, pay_note); an unknown or unclosed field cannot be saved. Fields are filled **after** parsing (a value can never become formatting or a link) and the applicant's name is stripped of formatting characters. **Pay is a free-text note only**: no rate, currency or hours are stored, calculated or exported. Letters say "independent contractor" (counsel to review the sample wording). The PDF is drawn with `@react-pdf/renderer` (`offer-pdf.tsx`, standard Helvetica, non-Latin text becomes "?"; it is a dependency approved by the owner and builds under `next build`).
- **Making an offer** (`makeOffer`; HR, Super Admin, recruiters; the applicant must be at the **Offer** stage; one live offer at a time): renders the letter, stores a **snapshot** of the final text in `offers.rendered_body` (editing the template later never changes a sent letter), and calls signing's `createEnvelope` with the applicant as an **outside signer** and an optional ELEVATE countersigner (signs after the applicant). **An offer's status is its envelope's status** (`offerStatus`: no envelope or draft = draft, out = sent, completed = signed, declined, expired, voided = withdrawn): no copies to keep in step. Offers can be saved as drafts, sent later, withdrawn (voids the envelope) and resent.
- **Outside signers** (`signing/external*.ts`, `esign_signers.user_id` is null, `external_email`/`external_name` set; exactly one of the two kinds): the applicant gets an emailed link `/sign/<token>` (a 256-bit random token, stored only as a SHA-256 hash; a resend replaces it), then must request a **6-digit code** emailed to the same address (valid 15 minutes, five wrong tries lock it, a new one needs a request, at most five codes an hour per person, all hashed) before they can read or sign. The right code starts a **two-hour session**: a random value in an httpOnly cookie (`elevate_sign_session`), only its hash stored. They read the PDF in the page and sign through `recordSignature()` (`signing/service.ts`), **the same rules as an ELEVATE user** (must be their turn, must have opened the document, consent, typed or drawn). The certificate records "email link and one-time code" as how they proved who they are, plus time and IP. Link and code emails go **straight out** (never queued, never BCC'd, never logged) and the link email carries no role, pay or client. After sealing they get a "signed copy ready" email; **the link they were using keeps working** (`previous_token_hash`) to open the signed copy, and links stay reachable for 30 days after a document ends. Public routes: `/sign/[token]` and `/api/sign/[token]/{code,verify,document,sign,decline}` (rate limits `signCode`, `signVerify`, `signPublic`; `/sign` is a public prefix, `/signing` is not). The immutability trigger on signed signer rows now allows only the link, code and session columns to change.
- **Hiring** (`hireCandidate`; **HR and Super Admin only**): needs a signed offer, or a written reason (stored in `onboarding_cases.hired_without_offer_reason`, audited). In one transaction: `createEmployeeRecord()` (`people/create.ts`, shared with "Add person": contractor, status onboarding, links an existing account with the same email), `markHired()` (`recruiting/service.ts`: stage, history, audit), an **onboarding case** (`talent.onboarding_cases`, which Phase 3.4 builds on), and an invitation via `ensureInvitation()` (`settings/invite.ts`, shared with Settings > Invitations) when they have no account; the invitation email goes out after the commit (`emailed: false` tells HR to share the Accept an invite steps). A work email that already exists rolls everything back. Retention never purges a hired person. The resume and the signed offer stay linked through the application and the onboarding case; copying them into the document vault comes with onboarding (3.4).
- Permissions: `offers.manage_templates`, `offers.hire` (HR, Super Admin), `offers.make` (plus recruiters), `offers.view` (plus a team lead on the job's hiring team). Tests: `src/modules/offers/merge.test.ts`, `tests/integration/offers.test.ts`, `tests/authz/offers-actions.test.ts`, `tests/e2e/offers.spec.ts` (no email service locally, so the e2e puts the applicant's link and session in the database; the emailed-code step is covered by the integration tests).

## Performance reviews and goals (Phase 4.1)

- `src/modules/reviews/`, tables in schema `talent`: `review_templates`, `review_cycles`, `reviews` (one per person per cycle), `review_responses` (self and lead), `review_calibrations`, `review_acknowledgments`, `goals`, `goal_notes`, `review_settings` (one row). Menu item **Reviews** (`/reviews`) with its own pages: `/reviews/[id]`, `/reviews/cycles/new`, `/reviews/cycles/[id]`, `/reviews/templates`, `/reviews/goals`.
- **Wording:** the plan's "probation (regularization)" review is an **early-engagement review** at month 3 and month 5 (1099 contractors, no regularization status). Counsel to confirm. Ratings are 1 to 5 with labels (needs improvement to outstanding). **No pay, raise or bonus field exists anywhere**; ratings are never converted into pay. No review content in emails or notifications (a link only).
- **Flow:** HR launches a cycle (quarterly, annual or early) from a template for everyone, some teams or chosen people (`launchReviewCycle`). The cycle **keeps its own copy of the questions**, so editing a template never changes a running cycle. Each review has the person's lead at launch (`lead_user_id`, HR can hand it to someone else with `reassignReviewer` before it is written). Steps: self review (optional, reminded) -> lead review (does not wait for the self review) -> HR calibration -> HR shares -> the person acknowledges ("I have read this", not "I agree", with an optional comment). `stageOf()` in `constants.ts` derives the stage from the timestamps.
- **Visibility** (`visibility()`, pure and tested): HR sees everything; the person sees their own self review, and the lead's feedback and final rating **only after HR shares**; the lead sees the self review **only after submitting their own** and the calibration only after sharing. If HR changed the lead's overall rating, the person is shown the final rating and the lead's written feedback but **not the lead's original rating** (`leadRatingHidden`); HR's reason for the change stays with HR. A changed rating needs a written reason. **Nobody writes the lead step for, calibrates or shares their own review** (another HR admin does). The Executive sees counts and averages only (`reviews.summary`), and an average is hidden below 5 reviews (`MIN_GROUP`).
- **Evidence:** `review_responses`, `review_calibrations` (newest row is current, only until shared) and `review_acknowledgments` are append-only (triggers reuse `talent.reject_change()`); a `reviews` row only moves forward (`reviews_guard`: a finished step cannot change, identity never changes, no delete). Audit rows never hold answers, notes or goal text.
- **Early-engagement reviews** (`runEarlyReviews`, daily 1:45 AM Phoenix, job `early-reviews`): a person with a start date gets a month 3 and a month 5 review on `startDate + 3 or 5 months` (month arithmetic clamps to the month end, `addMonths`). A milestone is opened for up to 31 days after its date (a job outage is made up) and **never back-filled** for people who started long ago; a unique index (`employee_id, milestone`) makes it idempotent. Each milestone and calendar month gets its own cycle ("Early-engagement review, month 3, 2026-10") using HR's chosen early template or the built-in short one; HR can switch it off (`setEarlyReviews`, Templates page). Due dates are +7, +14 and +21 days.
- **Reminders** (`runReviewReminders`, daily 8:45 Manila, job `review-reminders`): whoever has the next step of an open cycle's review gets one nudge a day once its due date is reached (`last_reminder_on`); HR gets one summary count. Both jobs are in the health registry.
- **Goals** (`goals`, `goal_notes`, `/reviews/goals`): simple goals (title, details, target date, status, progress notes), added and updated by the person, their chain of leads and HR (`goals.manage`); archived, never deleted. No weighting or scoring.

## Safe Voice (Phase 4.2)

- **Two parts.** `apps/safe-voice` is a separate minimal Next.js app (own Vercel project and subdomain, port 3100 locally) for reporters. `apps/elevate/src/modules/safevoice/` is the handler side inside ELEVATE (`/safe-voice-cases`, `/safe-voice-cases/[id]`, `/api/safe-voice-cases/attachments/[id]`). Tables `ops.safevoice_reports`, `safevoice_messages`, `safevoice_attachments` (migration 0037; RLS on, **no public policy**). The Safe Voice app has no Supabase keys, no auth and none of ELEVATE's secrets.
- **Two database roles, both created by the migration with NOLOGIN** (ops gives them a password out of band with `ALTER ROLE ... LOGIN PASSWORD`; no secret is ever in the repo): `safevoice_app` (the reporter app: INSERT on the three tables, SELECT only of the columns a reporter is shown plus the credential columns it compares; no UPDATE, no DELETE, **cannot read report text, category or attachment bytes**) and `safevoice_handler` (ELEVATE: SELECT cases but **never `code_hash`, `pass_salt`, `pass_hash`**, INSERT handler messages, UPDATE only `status`, `outcome`, `closed_day`, `handler_notified`). Policies are per role (`TO safevoice_app` / `TO safevoice_handler`), including `WITH CHECK (author = 'reporter')` / `'handler'` so neither can write as the other. Triggers refuse rewriting a report's text or credentials and deleting any report or message, even for the owner. ELEVATE reads the tables only through `src/modules/safevoice/handler-db.ts` (`svdb`, env `SAFEVOICE_HANDLER_DATABASE_URL`), never through `db`. Without that variable the cases page says "not connected" and the hourly job fails visibly in production.
- **Nothing identifying is stored or logged.** No user id, address, user agent, referrer, cookie, file name or time of day. **Time decision: the UTC day only** (`created_day`, `sent_day`, `closed_day` are `date`; no timestamp column exists in these tables, a test asserts it). Order inside a case is an identity `seq`. Ordering across cases is by day, then id. The reporter sees days, labelled UTC. `src/proxy.ts` deletes `cookie`, `authorization`, `user-agent` and `referer` from every request before any route runs; no code in the app may read or set a cookie or touch browser storage (`apps/safe-voice/tests/privacy.test.ts` scans the source: no `cookies()`, `next/headers`, `localStorage`, `Set-Cookie`, only the headers `x-forwarded-for`, `x-real-ip`, `content-length`, only error class names logged, no third-party URLs). `next.config.ts` turns off dev request logging, sets `no-store`, `Referrer-Policy: no-referrer`, a strict CSP, `noindex`. Platform request logs and log drains cannot be controlled from code: `docs/SETUP.md` section 14b lists what to switch off. The page uses system fonts (no font service request).
- **Case code and passphrase.** Both random, from a 31-symbol alphabet with no 0, 1, I, L, O: code `SV-XXXX-XXXX-XXXX` (about 59 bits), passphrase four groups of five (about 99 bits). Stored only as `HMAC-SHA256(SAFEVOICE_PEPPER, "code:" + code)` (the lookup key) and `HMAC(pepper, scrypt(passphrase, 16-byte salt))`. **The pepper must never change** (it would lock out every reporter; keep copies in the password manager). Input is normalised (case, spaces, dashes and the `SV` prefix ignored). **A wrong code, wrong passphrase, malformed code and broken request all get the same 401 and the same body**, after the same work (a full scrypt against a dummy salt when no case exists, constant-time compare). A reply with wrong credentials is judged before the message or files, so no error can confirm a case exists. Nobody, the developer included, can recover or reset a code or passphrase.
- **No cookie, no session.** The reporter page sends the code and passphrase with every request (`/api/case/open`, `/api/case/reply`) and holds them only in React state (closing the tab forgets them). The reporter sees the thread, the status and the outcome; the app role cannot read the report text, so it is not echoed back.
- **Rate limits** (`apps/safe-voice/src/lib/rate-limit.ts`, Upstash, **fail closed in production**, open in development): `submit` 5 an hour per address, `open` 20 per 10 minutes per address, `perCode` 10 per 15 minutes for one code from anywhere (a wrong or unknown code counts the same). The limiter key is a keyed hash of the address that changes every UTC day (`limiterKey`) and exists only inside Upstash for the window; the address itself is never stored or logged. A hidden `website` field catches robots (believable answer, nothing stored).
- **Attachments** (`attachments.ts`): up to 3 files, 4 MB in total per request (Vercel's body limit), JPG, PNG or PDF, type taken from the **bytes**. Pictures are **decoded and re-encoded with sharp** (orientation applied, then no EXIF, GPS, ICC, XMP or text chunks; at most 2400 px a side; 40 megapixel input cap). PDFs are **rebuilt page by page with pdf-lib** into a new document with no Info, XMP, producer or dates, and with annotations, page metadata and thumbnails removed from the source pages first (copying brings every referenced object along, so removing from the copy would leave them in the file). Encrypted or damaged files, more than 40 pages, other types: refused with one message. Not covered, and the form says so: words and images visible on the page, and metadata inside pictures embedded in a PDF. **Decision: files are kept in Postgres (`safevoice_attachments.data`, `bytea`), not in Supabase Storage**, so the anonymous app needs no storage service key and no object metadata (names, upload times) ever exists; handlers download through the ELEVATE route (named `attachment-N`, `nosniff`, sandboxed CSP, PDFs as downloads, every open audited). **New dependency:** `sharp` in `apps/safe-voice` only (re-encoding pictures needs a decoder; it was already in the lockfile as Next's optional image dependency); `postgres`, `pdf-lib`, `zod`, `@upstash/*` are the versions ELEVATE already uses.
- **Who sees cases.** Only a person individually flagged `core.users.is_safevoice_handler` passes `safevoice.handle` (lists, reads, replies, status, close, attachments). **No role grants it: a Super Admin and HR Admin do not see cases unless also designated** (matrix rows unchanged). **Decision: only a Super Admin designates handlers** (existing `settings.set_safevoice_handler`, audited; the brief said Super Admin or HR, the stricter existing matrix row was kept; HR designation would be a matrix change). The Executive passes `safevoice.view_counts` (counts only, never a case). Everyone else: the menu item is hidden (`NavItem.access` now takes a list: any rule shows it), the page and queries refuse.
- **Counts** (`stats.ts`, pure): a category with **fewer than 5** reports is never shown with its number; hidden categories appear only as one combined row and only when that sum is itself at least 5; the all-reports total is shown only when nothing is hidden or the hidden sum is at least 5 (complementary suppression, so a hidden number cannot be worked out by subtraction). Handlers see the same stats card under their list.
- **Handling.** Status `new` -> `in_review` / `awaiting_reporter` -> `closed` with an outcome (substantiated, partly, not substantiated, no action, referred, could not be determined) and an optional closing message; the database requires an outcome exactly when a case is closed. A reply can ask the reporter to answer (sets `awaiting_reporter`). A closed case takes no reporter messages and no handler replies until a handler **reopens** it (`setSafevoiceCaseStatus`, clears the outcome). Handlers refer to a case as `SV-<first 8 of its id>` (not the reporter's code). "Needs a reply" = open and the last message is the reporter's (or none).
- **Audit** (`service.ts`, `queries.ts`, the attachment route): `safevoice.case_view`, `safevoice.reply`, `safevoice.status`, `safevoice.reopen`, `safevoice.close`, `safevoice.attachment_view`, with actor, case id, before/after status and outcome code, **never any report or message text** (a test searches the audit rows for the text). The case change runs in the restricted connection inside the main transaction that writes the audit row, so either failing rolls both back (the only gap is a failure of the very last commit).
- **Notifications** (`jobs.ts`, Inngest `safevoice-notify`, hourly at :20, in `health/registry.ts`): in-app only, relative link, **counts only** ("2 new reports and 1 new reply"), to every designated handler; then the rows are marked notified. Hourly and batched on purpose, so the time a handler is told cannot be matched to the moment someone reported. With **no handler designated** the Super Admins get one warning a day and nothing is marked, so a handler designated later is still told. No email is ever sent for Safe Voice.
- **How people reach it:** every signed-in person sees **Report a concern** (a plain link, new tab, `rel="noopener noreferrer"` so no referrer is sent) at the bottom of the ELEVATE menu under "Speak up". The address comes from `NEXT_PUBLIC_SAFEVOICE_URL` (a public address, not a secret); in development it defaults to `http://localhost:3100`, and in production with no value the link is simply not shown. It carries no tracking parameter. This is separate from the staff-only **Safe Voice cases** item (designated handlers and Executives).
- **Not built / left to counsel:** retention and deletion of old reports (nothing deletes them; triggers forbid it), a Safe Voice digest by email, and any way for a handler to message a reporter outside the case thread. Limits worth knowing: a reporter's own words or a visible detail in a picture can still identify them; someone with direct database access could still see the order reports arrived in (identity sequence) and database backups carry their own timestamps; the platform's request logs are outside the app's control (see SETUP 14b).
- **Migration numbering:** this phase is `0037_safe_voice` (journal idx 36 in this branch because `0036` belongs to performance reviews on another branch). When merged, the journal entries must be ordered `0036` then `0037` with `idx` 36 and 37, and the snapshot chain re-generated (`pnpm db:generate` should then report nothing to change). Its `when` is later than the other migration's on purpose, so a database that already ran one still runs the other.
- Tests: `apps/safe-voice` (`pnpm --filter safe-voice test`: codes, attachment metadata removal, rate limit fail-closed, privacy source scan), `src/modules/safevoice/safevoice.test.ts` (stats rules, lists equal in both apps), `tests/authz/safevoice-actions.test.ts` (every action and query for all six roles, with and without the handler flag), `tests/integration/safevoice.test.ts` (roles and grants, nothing identifying stored, no cookie set, identical failures, attachments clean, full handling flow, audit without text, counts hiding small categories, notification job). It imports the Safe Voice request handlers by relative path and runs them against the real database through the real `safevoice_app` role.

Assigning to someone separated or archived is refused; **returning from a separated person is allowed** (that is when it happens).

Status changes are audited with before and after.
- **Handed over by / received by** are the HR user ids stored on the assignment row and also in the audit entry (`asset.assign` with `handedOverBy`, `asset.return` with `receivedBy`). No signature or acknowledgment flow. Audit entries carry no serial numbers or notes (only whether a serial exists).

Matrix rows are in `tests/authz/matrix.test.ts`. A **team lead** sees an item only if it is or was with someone in their downline, and only those rows of its history; an **employee** sees an item only if it is or was theirs (so the link in a "return recorded" notice still opens), and only their own rows. HR alone sees notes, purchase date and who handed over or received. Anyone else gets "not found", the same as for a tag that does not exist. `listTeamAssets` is for leads only (HR reads the inventory).
- **QR codes** (`components/qr-code.tsx`): the library `qrcode.react` (`QRCodeSVG`, inline SVG, no canvas, about 20 KB) was added as the only new dependency, as the build plan names it; writing a QR encoder by hand is error-prone. The code encodes **only** `origin + /assets/<tag>`: the origin comes from the browser, so it is right on localhost, staging and production; no name, serial number or person. Scanning opens the page behind the normal sign-in and MFA gate; a signed-out person is sent to sign in and then, after the two-step code, back to the asset page (the `?next=` address is kept through `/login` and `/mfa`, and only same-site paths are accepted).

- **No scheduled job** (so nothing new in the health registry). Not built: bulk import, depreciation or cost, low-stock alerts, checking items in and out by scanning (a scan only opens the page), signed hand-over forms.
- **Integration tests can run side by side:** `TEST_DB_NAME` (letters, digits, underscore) overrides the throwaway database name `elevate_test`, so two people or worktrees do not drop each other's database.

- `src/modules/analytics/`; six summary tables in schema `ops` (prefix `analytics_`, migration 0039, RLS on, no policies): `headcount_daily`, `movement_monthly` (joiners, leavers, average and end headcount), `leave_monthly` (prize days used), `attendance_weekly`, `funnel_monthly`, `time_to_hire_monthly`. **Aggregates only: no column or row names a person.** Dashboards read only these tables, never the source tables.
- **Dimensions** (`dim_kind` + `dim_id`): `company` (nil uuid), `team`, `client`, and `downline` (everyone below one manager, direct and indirect: what a team lead sees). A person belongs to a group on a date by the **dated history**: `core.team_memberships`, `core.reporting_lines` and `core.client_assignments` (a person with no history rows falls back to the current `team_id`/`manager_id`). Headcount counts people from their start date (the record's creation date if none) through their end date inclusive (the archive date if archived with no end date).
- **Pure core** (unit tested): `calc.ts` (`buildSummaries`, `buildHiring`, `buildStart`, `turnoverPercent`), `suppress.ts`, `view.ts` (rows to what is shown), `dates.ts`, `export.ts`, `validators.ts`. `build.ts` loads the sources and writes.
- **Nightly job** `analytics-nightly` (2:50 AM Phoenix, after the 2:30 attendance rebuild; in `src/inngest/functions.ts` and `health/registry.ts`): `runAnalyticsNightly` builds through yesterday in the company zone. With no snapshots it **backfills 366 days**; otherwise it rebuilds the last 7 days plus any missed day inside the window (self-heal). `rebuildRange(from, to)` is the backfill function: it widens to whole weeks and months, deletes that range and rewrites it in one transaction (idempotent, no stale rows). Hiring tables are rebuilt for the whole window every night because a stage move changes an old application's funnel.
- **Definitions:** turnover for a month = leavers / average daily headcount of the month, in percent (not annualized). Leavers and joiners are attributed to the groups the person was in on their last or first day. Prize days used = usage minus reversals by the leave date (counts only). Attendance flags are **person-days** per week (a day with several extra-hours flags counts once; "extra hours" = extra_hours, rest_day_work or holiday_work), with the rate = flagged days / recorded days. The funnel counts applications that reached each stage, in the month they applied; time to hire = days from applied to hired, in the month of the hire.
- **Small groups are hidden** (`MIN_GROUP = 5`, `suppress.ts`, applied in `view.ts` and `queries.ts` on the server, so hidden numbers never reach the browser or the CSV): a month, week or day whose group had fewer than 5 people shows "fewer than 5" (monthly movement uses the smaller of the average and the end-of-month headcount); breakdowns by team, client and job merge small groups into "Other" and, if "Other" would itself be under 5 (which would reveal a hidden group by subtraction), also merge the smallest visible group; a group chosen through the address that is not in the visible list is treated as hidden. A funnel (all jobs) with fewer than 5 applicants is hidden; time to hire is hidden for fewer than 5 hires in the period (the hires count itself stays). Small groups are never named.
- **Who sees what:** `analytics.view` (HR and Super Admin all, Executive all read-only, Team Lead team): the company, or a team or client of at least 5 people (`?scope=team:<id>|client:<id>`); a team lead always gets their own downline whatever the address says, with no breakdowns; a lead with no people record sees a note. `analytics.view_hiring` (HR, Super Admin, Recruiter, Executive) adds the hiring section; a recruiter sees hiring only. `analytics.export` (HR, Super Admin): `exportAnalytics` returns a CSV of exactly what is displayed (long format Section/Period/Group/Metric/Value, hidden cells read "fewer than 5", `csvCell` protection), rate-limited with the `download` policy and audited as `analytics.export`. Never exposed: pay, sensitive fields, review ratings, Safe Voice data, any per-person row.
- **Inputs:** `?range=3|6|12` (months, default 12) and `?scope=` are checked in `validators.ts`; a bad value falls back to the default view, a bad export request is refused.
- **Charts** use **Recharts** (`components/series-panel.tsx`, dependency approved by the owner): each has a Chart/Table toggle with a paged data table and a text summary on the chart (`role="img"`). A hidden cell is null, so a line breaks and a bar is missing there. The page is `/analytics` (its own menu item).
- Tests: `src/modules/analytics/analytics.test.ts` (pure), `tests/authz/analytics-actions.test.ts`, `tests/integration/analytics.test.ts` (real Postgres: build, backfill, self-heal, history, who sees what, hidden groups, export, RLS), matrix row `analytics.export`.

## TalentHR import (Phase 5, part 1)

- `src/modules/imports/`, tables `ops.import_batches` and `ops.import_rows` (migration 0040, RLS on). Page: **Settings > Import from TalentHR** (`/settings/import`, `/settings/import/[id]`); permission `imports.manage` (HR and Super Admin only). **Real exports are never put in the repo, tests or a development database**: the real dry runs happen in the production system (the quarantine), and every test uses the invented files in `tests/fixtures/talenthr-export.ts` (same 45 columns as the real export).
- **Steps:** upload the CSV (route `/api/imports/stage`: 2 MB, 2,000 rows, rate limit `upload`) -> choose where each column goes and the date format (defaults for TalentHR's columns in `mapping.ts`; the choice is saved on the batch) -> the file is read into a **preview batch** (`stageBatch`: nothing is created) -> HR reads the rows (new, changed, unchanged, errors, warnings, paged) -> **commit** (`commitBatch`, one transaction; no emails, no accounts) -> reconciliation and sign-off. Rows with errors block the commit unless HR ticks "skip them". A row's issues name the field and the problem, never the value.
- **Quarantine:** each staged row is the normalized person **encrypted** with the field key (context `import_row:<batch>:<row>`); outcome, field names and issues are the only plain columns. The payload is wiped when the batch is committed or discarded, and a daily job (`import-purge`, 3:40 AM Phoenix, in the health registry) discards previews older than 14 days.
- **Defaults:** workers are imported as 1099 contractors. "Terminated" (or any termination date) means separated with that last working day; a future start date means onboarding. Department becomes a team and Job Title a position (both created if missing; new teams sit under a department called "Imported from TalentHR"). Pay rate and currency go to the encrypted sensitive fields (HR only, ELEVATE never computes pay). Birth date, civil status, phone, address, country (names to codes), emergency contact (needs name and a valid phone) map to the built-in fields. Location, Division, shirt size, onboarding date and the status text become **HR-only custom fields**. **Left out by default:** gender, citizenship, avatar, free-text "Compensation and Benefits", free-text notes, pay schedule, overtime, approvers: HR can map a column to a custom field in the screen, but custom fields are never for sensitive data.
- **Matching and re-imports:** people are matched by **work email** (case-insensitive), so a second dry run updates the same people ("changed" lists field names, "unchanged" changes nothing) and restores anyone a rollback archived. A person who **already has an ELEVATE account** keeps their status and dates: the file never changes them (a warning says so). Supervisors are linked through the TalentHR ID within the file and applied last through `applyReporting()` (dated, no loops); a refusal or a supervisor who is terminated or not in the file is a warning on that row, not a failure.
- **Rollback** (`rollbackBatch`): people the batch CREATED are **archived, never deleted**, unless they have signed in or have activity (clock events, leave, schedules, equipment); those are kept and counted. Changes the batch made to people who already existed are not undone. The ledger, history and audit log are append-only, so deleting is not possible by design.
- **Reconciliation** (`getReconciliation`, PDF at `/api/imports/[id]/reconciliation`, counts only): file versus ELEVATE for total people, current people, terminated people, skipped rows and managers that could not be set; HR signs off (audited `import.signoff`). Leave and documents are compared once pulled from the API (part 2).
- **Dates:** the screen asks for the format (month/day/year is TalentHR's), impossible dates are errors, and a bad birth date is only a warning (left empty).
- Tests: `src/modules/imports/imports.test.ts` (CSV, mapping, dates, countries, normalizing), `tests/authz/imports-actions.test.ts`, `tests/integration/imports.test.ts`, `tests/e2e/import.spec.ts`.

## TalentHR API pull and go-live (Phase 5, part 2)

- **API pull** (`src/modules/imports/pull.ts`, `talenthr-client.ts`, script `pnpm talenthr:pull`, tables `ops.import_pulls` and `import_pull_items`, migration 0041). TalentHR's API is a Postman-documented REST API at `https://pubapi.talenthr.io/v1` with HTTP basic auth; the client only ever sends GET requests, keeps under the 2,000 a minute limit, retries 429 and 5xx, and sends credentials only to TalentHR's own host (a file link on another host is fetched without them). The key is `TALENTHR_API_KEY` in the git-ignored `apps/elevate/.env.talenthr.local`, never in chat or the repo; `--probe` finds out whether it works as the user name or the password.
- **What it does:** for each TalentHR person whose work email matches a person in ELEVATE (so import the people CSV first): their **documents** are downloaded (10 MB, real type checked by bytes, JPG/PNG/PDF/DOCX only) and saved as real documents of the person under the document type "Imported from TalentHR" (private `employee-docs` bucket; a file already there, by SHA-256, is a duplicate); their **time-off budgets and requests** and the company's **jobs and applicants** are kept as **encrypted archives** (`import_pull_items.payload_enc`, readable only through `readArchive`). Skipped or failed files carry a short reason code (too_large, type_not_allowed, download_failed), never a name.
- **Excel upload:** the import screen also takes an `.xlsx` export (`xlsx.ts`, library `read-excel-file`, dependency approved by the owner; `write-excel-file` is a dev dependency used only to build invented test files). Only the first sheet is read, through the same table checks and mapping as a CSV; date cells become ISO dates. Before a spreadsheet (a zip) is opened its table of contents is read and a file that would unpack to more than 40 MB or 200 entries is refused.
- **Active applicants are loaded into recruiting** (`applicants.ts` pure rules, `applicants-pull.ts`, `recruiting/service.ts` `createImportedOpening` and `importApplication`; migration 0043 adds `import_pull_items.local_id` and the kinds `opening` and `application`). For each TalentHR job with at least one **active** applicant (a live application, not disqualified, with a usable email, whose step is not an ending such as hired, rejected, withdrawn, declined or talent pool): a **closed** job opening is created (HR reopens one to use it; no acknowledgment or rejection emails are enabled), each applicant becomes a candidate (an existing candidate with the same email keeps their own details) and an application at the nearest stage (`stageForStep`: offer, interview, assessment, screening, else applied), with the stage history noting the import, the application date and cover note kept, and the **resume** saved when TalentHR gives a PDF or DOCX up to 4 MB. Candidates carry the notice version `talenthr-import`. Nobody is emailed. Recruiters' internal notes in TalentHR are not imported. Closed, rejected and hired applicants stay only in the encrypted archive. `--no-applicants` skips it, and `--only` skips it too. Repeat runs skip what was loaded.
- **Leave is not loaded.** Prize days are rare at ERS (and the prize is sometimes cash or a coupon), so TalentHR balances are **not** written as opening-balance ledger rows and the screens do not feature them; the history is only archived. If HR ever wants specific balances, that is a small separate step to add.
- **Safety:** `talenthr:pull` refuses to run unless `ELEVATE_ENV=production`, needs `--as <HR or Super Admin email>`, supports `--dry-run` (counts only, writes nothing) and `--only a@x.com,b@x.com`, and is safe to repeat (items already imported are skipped; a skipped or failed one is replaced when retried). Every run is audited (`import.pull`, counts only). Tests use a fake TalentHR (`tests/integration/imports-pull.test.ts`); the real API is never called from tests.
- **Reconciliation** now also compares the documents TalentHR holds for the batch's people with those imported (and counts people with a document that was not imported); leave histories archived are shown as a count.
- **Go-live checklist** (`/settings/go-live`, `imports.manage`, table `ops.golive_items`, migration 0042): automatic rows (required production settings present by NAME only, privacy notice and monitoring policy published with real text, at least two Safe Voice handlers, a signed-off reconciliation, how many people have accounts) and manual steps HR ticks (domain and DNS, a backup restore test, error alerts, sign-in emails, sending domain, counsel's read, pilot team, invitations in waves, help for HR, the two-week parallel run, archive and cancel TalentHR). The settings check describes the deployment you are looking at, so open it on the live site.
- Tests: `src/modules/imports/golive.test.ts`, `tests/integration/imports-pull.test.ts`, `tests/e2e/go-live.spec.ts`, and the import authz test covers the checklist action and query.

## Adding a permission or action

1. Add the action to that module's `permissions.ts` (`"<module>.<action>": { roles: { hr_admin: "all", ... } }`). Scopes: own, team, all. Nothing listed = no access.
2. Add the matching row to `tests/authz/matrix.test.ts` (written by hand from the architecture plan, never derived from the registry). The suite fails if an action has no row.
3. In the action or query: `const user = await requireUser()` first (outside `runAction`), then `await authorize(user, "<module>.<action>", resource)` inside it. Return `runAction(...)` results. Pages wrap queries in `orNotFound()`.
4. Write `writeAudit()` inside the same transaction as the change. Pass `tx`.
5. Add the action to a per-role authz test like `tests/authz/settings-actions.test.ts`.
6. `team` scope needs `managerChainUserIds` on the resource (Phase 1.2); without it team access is denied.

The audit log is insert-only at the database level (trigger). Test data written to it stays until `supabase db reset`.

## Encrypting sensitive fields

`src/lib/crypto.ts`: `fieldCrypto().encrypt(value, context)` / `.decrypt(stored, context)`. The context string binds a value to its place, for example `employee_sensitive:tin:<employeeId>`, so a ciphertext copied to another row or column will not decrypt. Always use the same context when reading and writing. Decrypt only after `authorize()`, call `writeAudit()` with action `sensitive.view` (field name, never the value), and show `maskValue()` by default. Rotation: put the new key first in `FIELD_ENCRYPTION_KEYS` (`v2:...,v1:...`), run the re-encrypt job until `needsReencrypt()` is false for every row, then drop the old key. Losing every copy of a key makes its fields unreadable, so keep copies in the password manager.

## Seed data

`pnpm db:seed` creates one fake sign-in account per role (`seed.<role>@example.com`; password in the git-ignored `apps/elevate/.seed-credentials.local`) and refuses to run against production or any remote database unless `ELEVATE_ENV=staging`. The deterministic 40-employee dataset lives in `src/lib/seed/data.ts` and is inserted with clients, assignments, encrypted fake IDs, 2 departments, 6 teams, the position catalog and a reporting tree (Employee account reports to the Team Lead account, who reports to the Executive account). Re-running fills only what is missing.

## Security and privacy rules

- **MFA:** the `(app)` layout and `proxy.ts` require AAL2. No page or action works at AAL1 except MFA enrollment/challenge.
- **Roles:** Super Admin, HR Admin, Team Lead, Recruiter, Executive, Employee. Scopes: own, team, all. The matrix in `docs/architecture-plan.md` §3 is the source of truth; `src/lib/authz.ts` implements it; `tests/authz/` must cover every action for every role.
- **Sensitive fields** (government IDs: TIN, SSS, PhilHealth, Pag-IBIG; bank/payout details; pay rates) live only in `core.employee_sensitive`, encrypted with `src/lib/crypto.ts` (AES-256-GCM, versioned keys). Decrypt only for Super Admin, HR Admin, or the employee (masked by default). Every decrypt writes an audit entry.
- **Audit:** call `writeAudit()` for logins, role changes, approvals, exports, imports, sensitive views, and every create/update/delete on employee data (store before/after JSON, minus secrets).
- **RLS:** every new table gets `ENABLE ROW LEVEL SECURITY` in its migration with no public policies.
- **Secrets:** only `NEXT_PUBLIC_*` values may reach the browser. Never log tokens, passwords, government IDs or file contents. Sentry must not receive PII.
- **Files:** private buckets only; signed URLs expire in 60 seconds; allowlist PDF, JPG, PNG, DOCX up to 10 MB; check MIME type server-side.
- **Rate limit** login, careers apply, and Safe Voice endpoints with Upstash.
- **Safe Voice** is anonymous: it runs on its own subdomain/app, never reads auth cookies or sessions, never stores user ID, IP, user agent or file metadata. Reporters get a random case code + passphrase (hashed with a pepper). Only designated handlers can read cases.
- **No patient data (HIPAA):** no module may have fields for client patient information. Upload screens show a warning not to upload client records.
- **Real data only in production.** Seeds and tests use fake data (Filipino and US names, fake IDs).

## Conventions

- File names kebab-case; React components PascalCase; server actions verb-first (`approveLeaveRequest`).
- Return `{ ok: true, data } | { ok: false, error }` from actions; show errors with toasts; never leak stack traces.
- UI copy: plain, short, sentence case. Brand: ERS colors via Tailwind theme tokens in `globals.css`.
- Accessibility: labels on every input, keyboard-usable dialogs and boards, 4.5:1 contrast.
- Write tests with each feature: Zod validators, authz for every new action, one Playwright happy path per flow.
