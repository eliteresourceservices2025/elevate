## Safe Voice (Phase 4.2)

- **Two parts.** `apps/safe-voice` is a separate minimal Next.js app (own Vercel project and subdomain, port 3100 locally) for reporters. `apps/elevate/src/modules/safevoice/` is the handler side inside ELEVATE (`/safe-voice-cases`, `/safe-voice-cases/[id]`, `/api/safe-voice-cases/attachments/[id]`). Tables `ops.safevoice_reports`, `safevoice_messages`, `safevoice_attachments` (migration 0037; RLS on, **no public policy**). The Safe Voice app has no Supabase keys, no auth and none of ELEVATE's secrets.
- **Two database roles, both created by the migration with NOLOGIN** (ops gives them a password out of band with `ALTER ROLE ... LOGIN PASSWORD`; no secret is ever in the repo): `safevoice_app` (the reporter app: INSERT on the three tables, SELECT only of the columns a reporter is shown plus the credential columns it compares; no UPDATE, no DELETE, **cannot read report text, category or attachment bytes**) and `safevoice_handler` (ELEVATE: SELECT cases but **never `code_hash`, `pass_salt`, `pass_hash`**, INSERT handler messages, UPDATE only `status`, `outcome`, `closed_day`, `handler_notified`). Policies are per role (`TO safevoice_app` / `TO safevoice_handler`), including `WITH CHECK (author = 'reporter')` / `'handler'` so neither can write as the other. Triggers refuse rewriting a report's text or credentials and deleting any report or message, even for the owner. ELEVATE reads the tables only through `src/modules/safevoice/handler-db.ts` (`svdb`, env `SAFEVOICE_HANDLER_DATABASE_URL`), never through `db`. Without that variable the cases page says "not connected" and the hourly job fails visibly in production.
- **Nothing identifying is stored or logged.** No user id, address, user agent, referrer, cookie, file name or time of day. **Time decision: the UTC day only** (`created_day`, `sent_day`, `closed_day` are `date`; no timestamp column exists in these tables, a test asserts it). Order inside a case is an identity `seq`. Ordering across cases is by day, then id. The reporter sees days, labelled UTC. `src/proxy.ts` deletes `cookie`, `authorization`, `user-agent` and `referer` from every request before any route runs; no code in the app may read or set a cookie or touch browser storage (`apps/safe-voice/tests/privacy.test.ts` scans the source: no `cookies()`, `next/headers`, `localStorage`, `Set-Cookie`, only the headers `x-forwarded-for`, `x-real-ip`, `content-length`, only error class names logged, no third-party URLs). `next.config.ts` turns off dev request logging, sets `no-store`, `Referrer-Policy: no-referrer`, a strict CSP, `noindex`. Platform request logs and log drains cannot be controlled from code: `docs/SETUP.md` section 14b lists what to switch off. The page uses system fonts (no font service request).
- **Case code and passphrase.** Both random, from a 31-symbol alphabet with no 0, 1, I, L, O: code `SV-XXXX-XXXX-XXXX` (about 59 bits), passphrase four groups of five (about 99 bits). Stored only as `HMAC-SHA256(SAFEVOICE_PEPPER, "code:" + code)` (the lookup key) and `HMAC(pepper, scrypt(passphrase, 16-byte salt))`. **The pepper must never change** (it would lock out every reporter; keep copies in the password manager). Input is normalised (case, spaces, dashes and the `SV` prefix ignored). **A wrong code, wrong passphrase, malformed code and broken request all get the same 401 and the same body**, after the same work (a full scrypt against a dummy salt when no case exists, constant-time compare). A reply with wrong credentials is judged before the message or files, so no error can confirm a case exists. Nobody, the developer included, can recover or reset a code or passphrase.
- **No cookie, no session.** The reporter page sends the code and passphrase with every request (`/api/case/open`, `/api/case/reply`) and holds them only in React state (closing the tab forgets them). The reporter sees the thread, the status and the outcome; the app role cannot read the report text, so it is not echoed back.
- **Rate limits** (`apps/safe-voice/src/lib/rate-limit.ts`, Upstash, **fail closed in production**, open in development): `submit` 5 an hour per address, `open` 20 per 10 minutes per address, `perCode` 10 per 15 minutes for one code from anywhere (a wrong or unknown code counts the same). The limiter key is a keyed hash of the address that changes every UTC day (`limiterKey`) and exists only inside Upstash for the window; the address itself is never stored or logged. A hidden `website` field catches robots (believable answer, nothing stored).
- **Attachments** (`attachments.ts`): up to 3 files, 4 MB in total per request (Vercel's body limit), JPG, PNG or PDF, type taken from the **bytes**. Pictures are **decoded and re-encoded with sharp** (orientation applied, then no EXIF, GPS, ICC, XMP or text chunks; at most 2400 px a side; 40 megapixel input cap). PDFs are **rebuilt page by page with pdf-lib** into a new document with no Info, XMP, producer or dates, and with annotations, page metadata and thumbnails removed from the source pages first (copying brings every referenced object along, so removing from the copy would leave them in the file). Encrypted or damaged files, more than 40 pages, other types: refused with one message. Not covered, and the form says so: words and images visible on the page, and metadata inside pictures embedded in a PDF. **Decision: files are kept in Postgres (`safevoice_attachments.data`, `bytea`), not in Supabase Storage**, so the anonymous app needs no storage service key and no object metadata (names, upload times) ever exists; handlers download through the ELEVATE route (named `attachment-N`, `nosniff`, sandboxed CSP, PDFs as downloads, every open audited). **New dependency:** `sharp` in `apps/safe-voice` only (re-encoding pictures needs a decoder; it was already in the lockfile as Next's optional image dependency); `postgres`, `pdf-lib`, `zod`, `@upstash/*` are the versions ELEVATE already uses.
- **Who sees cases.** Only a person individually flagged `core.users.is_safevoice_handler` passes `safevoice.handle` (lists, reads, replies, status, close, attachments). **No role grants it: a Super Admin and HR Admin do not see cases unless also designated** (matrix rows unchanged). **Decision: only a Super Admin designates handlers** (existing `settings.set_safevoice_handler`, audited; the brief said Super Admin or HR, the stricter existing matrix row was kept; HR designation would be a matrix change). The Executive passes `safevoice.view_counts` (counts only, never a case). Everyone else: the menu item is hidden (`NavItem.access` now takes a list: any rule shows it), the page and queries refuse.
- **Counts** (`stats.ts`, pure): a category with **fewer than 5** reports is never shown with its number; hidden categories appear only as one combined row and only when that sum is itself at least 5; the all-reports total is shown only when nothing is hidden or the hidden sum is at least 5 (complementary suppression, so a hidden number cannot be worked out by subtraction). Handlers see the same stats card under their list.
- **Handling.** Status `new` -> `in_review` / `awaiting_reporter` -> `closed` with an outcome (substantiated, partly, not substantiated, no action, referred, could not be determined) and an optional closing message; the database requires an outcome exactly when a case is closed. A reply can ask the reporter to answer (sets `awaiting_reporter`). A closed case takes no reporter messages and no handler replies until a handler **reopens** it (`setSafevoiceCaseStatus`, clears the outcome). Handlers refer to a case as `SV-<first 8 of its id>` (not the reporter's code). "Needs a reply" = open and the last message is the reporter's (or none).
- **Audit** (`service.ts`, `queries.ts`, the attachment route): `safevoice.case_view`, `safevoice.reply`, `safevoice.status`, `safevoice.reopen`, `safevoice.close`, `safevoice.attachment_view`, with actor, case id, before/after status and outcome code, **never any report or message text** (a test searches the audit rows for the text). The case change runs in the restricted connection inside the main transaction that writes the audit row, so either failing rolls both back (the only gap is a failure of the very last commit).
- **Notifications** (`jobs.ts`, Inngest `safevoice-notify`, hourly at :20, in `health/registry.ts`): in-app only, relative link, **counts only** ("2 new reports and 1 new reply"), to every designated handler; then the rows are marked notified. Hourly and batched on purpose, so the time a handler is told cannot be matched to the moment someone reported. With **no handler designated** the Super Admins get one warning a day and nothing is marked, so a handler designated later is still told. No email is ever sent for Safe Voice.
- **How people reach it:** every signed-in person sees **Report a concern** (a plain link, new tab, `rel="noopener noreferrer"` so no referrer is sent) at the bottom of the ELEVATE menu under "Speak up". The address comes from `NEXT_PUBLIC_SAFEVOICE_URL` (a public address, not a secret); in development it defaults to `http://localhost:3100`, and in production with no value the link is simply not shown. It carries no tracking parameter. This is separate from the staff-only **Safe Voice cases** item (designated handlers and Executives).
- **Not built / left to counsel:** retention and deletion of old reports (nothing deletes them; triggers forbid it), a Safe Voice digest by email, and any way for a handler to message a reporter outside the case thread. Limits worth knowing: a reporter's own words or a visible detail in a picture can still identify them; someone with direct database access could still see the order reports arrived in (identity sequence) and database backups carry their own timestamps; the platform's request logs are outside the app's control (see SETUP 14b).
- **Migration numbering:** this phase is `0037_safe_voice` (journal idx 36 in this branch because `0036` belongs to performance reviews on another branch). When merged, the journal entries must be ordered `0036` then `0037` with `idx` 36 and 37, and the snapshot chain re-generated (`pnpm db:generate` should then report nothing to change). Its `when` is later than the other migration's on purpose, so a database that already ran one still runs the other.
- Tests: `apps/safe-voice` (`pnpm --filter safe-voice test`: codes, attachment metadata removal, rate limit fail-closed, privacy source scan), `src/modules/safevoice/safevoice.test.ts` (stats rules, lists equal in both apps), `tests/authz/safevoice-actions.test.ts` (every action and query for all six roles, with and without the handler flag), `tests/integration/safevoice.test.ts` (roles and grants, nothing identifying stored, no cookie set, identical failures, attachments clean, full handling flow, audit without text, counts hiding small categories, notification job). It imports the Safe Voice request handlers by relative path and runs them against the real database through the real `safevoice_app` role.
