# Recruiting, signing, offers and onboarding

> Moved out of CLAUDE.md to keep that file short. These are the full working notes for this area: read them before changing it. The hard rules are repeated in CLAUDE.md's "Module notes" index.

## Recruiting (Phase 3.1)

- `src/modules/recruiting/`, schema `talent`. **Applicants are not employees**: `talent.candidates` (one per email, case-insensitive), `applications` (one per candidate and job), stage history, notes, interviews, interviewers, scorecards, applicant emails, one-row settings. Stages are fixed (`constants.ts`): applied, screening, interview, assessment, offer, hired, rejected. Rejected has a `close_kind` (rejected or withdrawn). A hire is final; a rejected application is reopened by moving it to a stage. **"Hired" only marks the application**: creating the person record and onboarding come with offers (3.3).
- **Public pages** (no sign-in, indexable): `/careers` (open jobs only) and `/careers/[id]` with the apply form. The form posts to `/api/careers/apply` (a route handler, not a server action): Upstash rate limit `careers` (5 an hour per address, fails closed in production), honeypot field `website` (a filled one gets the same "ok" and stores nothing), privacy consent required (the published privacy notice version is stored with the candidate), resume PDF or DOCX up to **4 MB** (Vercel's body limit; checked by its bytes, SHA-256 stored) written by the server to the private bucket `recruiting-docs` (`pnpm storage:setup`). Applying twice to the same job looks the same to the applicant and adds nothing; applying to a second job replaces the resume with the newest file. Public pages say "contractor", never promise pay or benefits (the pay note is free text). No fields for client or patient information anywhere.
- **Careers page and readable addresses** (migration 0050): a job ad has a readable `slug` (`/careers/virtual-assistant-medical-billing`, made from the title, numbered when taken, editable only while the job is a draft because the link may be shared; `recruiting/slug.ts`). The old `/careers/<id>` link still works and redirects to the readable one (`getPublicOpening` takes either). The page's own title, introduction (Markdown) and one wide **banner** live in `talent.careers_page` (one row), edited at `/recruiting/careers-page` (`recruiting.manage_careers_page`: HR, Super Admin, recruiters). The browser crops the banner to 1600x400 and the server re-checks it (`cleanJpeg`, wide only, metadata removed), stores it in `company-docs/careers/banner/` and serves it at the public `/api/careers/banner?v=<time>`. Staff links to the public page ("View careers page" on Recruiting, "View job ad" on an open job) open in a new tab. **Questions about applying go to `elitetsp@ersva.com`** (`careersAddress()`, overridable with `CAREERS_EMAIL`; shown in the careers footer), never to the technical support address `elitehelpdesk@ersva.com`, which is only for ELEVATE trouble (login screen, Contact support). In the apply form, "privacy notice" in the consent line is a link to `/privacy` that opens in a new tab and does not tick the box.
- **Access:** `recruiting.view` and `recruiting.download_resume` are "all" for HR, Super Admin and recruiters, and "team" for a team lead, where the resource's chain is **that opening's hiring team** (`authorizeForOpening`, `openingHiringTeam`). Only HR, Super Admin and recruiters create jobs, move and close applications and schedule interviews. The Executive gets counts only (`recruiting.summary`). `NavItem.access` hides the Recruiting item from roles with none of these; the page 404s for them.
- **Board** (`/recruiting/[id]`): drag a card or use its "Move to" menu (**dnd-kit** `@dnd-kit/core`: drag by the grip with a mouse, a finger (150 ms press so scrolling still works) or the keyboard: space, left and right arrows jump a column, space; the "Move to" menu is the fallback). Each applicant has a page (`/recruiting/applications/[id]`) with details, resume (60-second signed link, audited as `recruiting.resume_view`), stage controls, notes, interviews, scorecards and history. Every move writes `talent.application_stage_history` (**append-only trigger**) and an audit row.
- **Interviews** are scheduled with a time, length, place or link and one or more interviewers (HR, Super Admin, recruiters, team leads). Interviewers get an `.ics` invite through the normal email queue (kind `invite`, no applicant name in the email) and a notification; the applicant gets the invite by the applicant email queue if the recruiter leaves the box ticked. Cancelling sends a cancellation. Interviews can also be created on Google Calendar (below).
- **Google Calendar for interviews** (Phase 3.1b, `google.ts`, `calendar.ts`): HR, Super Admin and recruiters connect **their own** calendar (Recruiting page card; `/api/google/connect` then `/api/google/callback`, with a one-time `state` cookie checked in constant time, and the MFA session re-checked). Scope `calendar.events` plus `openid email`. The refresh token is stored in `talent.calendar_connections` **encrypted with the field-encryption key bound to the user** (`google_calendar:<userId>`); access tokens are never stored. Add the `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (a separate client from Supabase sign-in, `docs/SETUP.md` 6b); with none, the card says it is not set up and everything uses `.ics`. `scheduleInterview` first creates the event on the **scheduler's own** calendar (event id derived from the interview id, so a retry cannot duplicate it; Meet link requested; guests are the interviewers' sign-in emails and, if ticked, the applicant; the title names the job, never the applicant) and stores `calendar_mode = 'google'`, `google_event_id`, `meet_link`, `calendar_user_id`; **ELEVATE then sends no .ics** for that interview (Google invites), though interviewers still get the in-app notification. If the scheduler is not connected, or Google fails or refuses, the interview falls back to the `.ics` emails with a warning, and **scheduling never fails because of Google**. An `invalid_grant`/401 marks the connection `needs_reconnect` (Testing-mode External apps expire tokens after 7 days; Internal or published apps do not). If saving the interview fails after the event was created, the event is deleted. Cancelling deletes the event with the organizer's connection (any HR admin can cancel); if that fails the interview is still cancelled and the screen says to delete the Google event by hand. Tests use `setGoogleClient(fake)`; **never call Google from tests**. Rotating `FIELD_ENCRYPTION_KEYS` does not re-encrypt these tokens: keep the old key until people reconnect, or extend the re-encrypt job.
- **Scorecards** (`talent.scorecards`, **append-only**, one per interviewer per interview, only after the interview has started, never editable): four ratings 1 to 5, a recommendation and a reason. An interviewer sees the others' scorecards only after submitting their own; HR, Super Admin and recruiters who are not interviewers on that interview see all.
- **Invitations are emailed** (`createInvitation` -> `sendInvitationEmail`, `settings/invitation-email.ts`): sent straight away when an email service is configured, never queued, never logged; the action returns `emailed: false` when nothing was sent and the screen then tells the admin to share the "Accept an invite" steps. The invitation is saved either way. **Sender address:** use a monitored address, never `no-reply` (inbox providers distrust one-way senders), and set `EMAIL_REPLY_TO`. Sign-up confirmation and password-reset mails come from **Supabase Auth**, not from this sender (local: Mailpit at :54324; production: custom SMTP).
- **Applicant emails** (`talent.candidate_emails`, job `candidate-email-sender` every 30 minutes, own cap `CANDIDATE_EMAIL_DAILY_BUDGET`, default 20): "received" (per-job switch), rejection (only when the recruiter ticks it, and the job allows it) and interview invites. They never contain scores, notes or reasons. `EMAIL_APPLICANT_BCC` (optional) adds a silent copy of each to a shared mailbox such as talent acquisition's. With no email provider key they wait in the queue.
- **Retention** (`runRecruitingRetention`, daily 3:30 AM Phoenix, job `recruiting-retention`): **off until HR switches it on** (Recruiting page, `recruiting.manage_retention`); the periods default to **12 months after a rejection and 6 after a withdrawal and need counsel's approval**. When every application of a candidate has been closed longer than its period (never for a hired person or anyone with a live application), the candidate row is anonymized (name, email, phone, country, resume file removed), notes and applicant emails deleted, scorecard free text replaced with "[removed]", application notes cleared; counts and stage history stay. The append-only triggers allow this only inside a transaction that sets `talent.retention = 'on'` (set by that job alone).
- Tests: `tests/integration/recruiting.test.ts` (apply, history, who sees what, scorecard visibility, emails, retention), `tests/authz/recruiting-actions.test.ts`, `tests/e2e/recruiting.spec.ts`. Integration tests use `FakeStorage.write`.

## The ATS layer (Phase 3.5): applicants list, source and tags, keyword match, talent pool, duplicates, reports, wording

Built on top of the board; stages stay fixed. Migrations 0091 (not qualified), 0093 to 0096. Tests: `tests/integration/recruiting.test.ts`, `tests/e2e/ats.spec.ts`, `src/modules/recruiting/*.test.ts`.

- **Not qualified** is a third `close_kind` next to rejected and withdrawn (retention like rejected, its own history note and email wording). Closing and moving are `moveInTx` / `closeInTx` in `transitions.ts`, shared by the single actions and the bulk action.
- **All applicants** (`/recruiting/applicants`, menu item "Applicants", `recruiting.view`, team leads see only their jobs): `listApplicants` filters in the database (name or email as plain text with LIKE characters escaped, job, stage, how it closed, source, tag, keyword match, talent pool, applied dates in the company zone) and pages there. The address is parsed by the pure `parseApplicantFilters` (anything unknown means "no filter"). Removed (anonymized) applicants show no name or email and are never matched by a search. A table from the tablet width, cards below it.
- **Source and tags** (`recruiting.tag`: HR, Super Admin, recruiters): the apply form asks "How did you hear about this job?" (optional; `?src=linkedin` pre-selects; an unknown value is ignored); staff can change it. `talent.tags` is a shared catalog (names unique ignoring case, archived not erased), `application_tags` links them (10 at most per application).
- **Bulk actions** (`recruiting.bulk`, up to 100): move (never to Hired: hiring stays one person at a time from an offer), close, add or remove a tag, add or remove from the pool. Each application runs in its own transaction; failures are returned with the reason and the rest still go through; history and audit rows are the same as one by one, plus one `recruiting.bulk` summary row. The checkboxes are server-rendered with `form="bulk-form"`; **never name them `id`** (it shadows `form.id`).
- **Resume keyword match** (`keywords.ts`, `resume-text.ts`): recruiters list must-have (70%) and nice-to-have (30%) keywords per job; at apply time the resume is read **on our server** (`unpdf` for PDF, `mammoth` for DOCX, 10 s limit, 200,000 characters at most) and only the percentage, the found and missing keywords, when, and a key of the keyword lists are stored. **The resume text is never stored or sent anywhere, and there is no AI.** It is a reading aid: it never rejects, never uses anything about the person (a test scans recruiting code for the voluntary self-identification fields), and a scan with no text scores nothing. `rescoreOpening` (the job board's "Re-score resumes") reads the stored resumes again after the keywords change; the applicant page says "Keywords changed since" until then.
- **Talent pool** (`recruiting.pool`): the apply form has an optional "keep my details for 12 months" box (`POOL_MONTHS`, counsel to confirm). Only someone who ticked it can be put in the pool (single or bulk); pool members are skipped by the retention job while the consent runs, and `expireTalentPool` (first step of the daily retention job, even when retention is off) takes expired people out so the normal periods apply again. `addPoolMemberToOpening` starts a new application for another open job ("Added from the talent pool").
- **Possible duplicates** (`/recruiting/applicants/duplicates`, `recruiting.merge`: HR and Super Admin): same phone number (last 10 digits) or same name; pure `groupDuplicates` only suggests. `mergeCandidates` moves the applications to the kept record, fills blanks, carries a longer pool consent, deletes the emptied record's self-identification answers, and leaves it as a "Merged duplicate" row with `merged_into`; refused when both applied for the same job or for a removed applicant. Erasing an application also removes its tag links.
- **Reports** (`/recruiting/reports`, `recruiting.reports`: HR, Super Admin, recruiters; counts only, no names): how far applications got (cumulative, so someone moved past a stage counts at the skipped ones), median time in each stage (from the append-only history), where applicants come from and how many reached interview or were hired, how applications ended, and open applications waiting 14 days or more. There is no per-recruiter performance report on purpose.
- **Applicant email wording** (`/recruiting/email-templates`, `recruiting.manage_email_templates`: HR and Super Admin): the "received", "not moving forward" and "not qualified" emails can be reworded (plain text, only `{{first_name}}` and `{{job_title}}`, validated by `validateTemplate`, escaped when the HTML is built). `talent.email_templates` has a row only once HR saves their own; "Use the built-in wording" deletes it. Interview invitations stay fixed. The audit row names the email, never its words.

## ELEVATE Sign (Phase 3.2)

- `src/modules/signing/`, tables `docs.esign_templates`, `esign_envelopes`, `esign_signers`, `esign_events`; files in the private bucket **`signed-docs`** (`pnpm storage:setup`). The menu item is **Signing** (`/signing`: To sign, All documents and Templates for HR; `/signing/new`; `/signing/[id]`). The public **`/verify`** page and its route `/api/signing/verify` need no sign-in.
- **Flow:** HR uploads an 8 MB, 100-page PDF (or picks a template) and the signers, in order or all at once (`createEnvelope()` in `service.ts` is the one entry point; **offers (3.3) and onboarding (3.4) call it**). Creation goes through route handlers `/api/signing/envelopes` and `/api/signing/templates` (large files; `requireUser()` and `authorize()` first, rate limit `upload`). **Signers must have an ELEVATE account** (they sign while signed in at AAL2). People outside the company (a candidate with an offer) sign as **outside signers** (see Offers and hiring).
- **Signing rules** (`actions.ts`): a signer must have **opened the document** (recorded as a `viewed` event), tick the consent (`CONSENT_TEXT`, version stored), then type (Latin-1 letters only, drawn in a standard italic font) or draw (a PNG up to 60 KB and 1000x400, checked by its bytes) their signature. Sequential order wakes the next signer(s) (`signersToActivate`); a decline ends the envelope (others cancelled, HR told); HR can void before everyone has signed; envelopes expire after 14 days by default; reminders every 3 days. IP comes from the request and the sign-in methods (e.g. "password, totp") from the auth server (`session.ts`), never from the browser. Emails to signers carry no titles or names.
- **Sealing** (`sealEnvelope`, `seal.ts` pure): reads the original, checks it still matches its SHA-256, adds a **signature page** (signatures are not placed on the original pages) and a **certificate** (document, reference `ES-XXXXXXXX`, signers with UTC, Manila and Arizona times, IP, how they signed in, event log), stores the sealed copy and its SHA-256 and completes the envelope. It runs after the last signature; if it fails the signature stands and the 30-minute **`esign-seal-sweep`** job finishes it (safe to repeat). Daily **`esign-reminders`** expires and reminds. Both are in the health registry.
- **Evidence is immutable** (triggers in migration 0030): `esign_events` is append-only and **hash-chained** (`chain.ts`; HR sees "Chain intact" or "broken" on the page), a signed signer row never changes, a sent envelope's original and a sealed copy cannot change, a finished envelope's status is final, and only a draft can be deleted (a discarded draft is voided, keeping its log). Originals are kept even for discarded drafts. **Retention of signed documents is not automated** (counsel to decide); nothing deletes them.
- **Documents are viewed in the page, not downloaded:** `DocumentViewer` (`src/components/document-viewer.tsx`) shows a PDF in an iframe from our own authenticated route (`/api/signing/[id]/document`, `/api/recruiting/resume/[applicationId]`), which runs the same checks as the download link (`openSigningDocument`, `openResume`), audits the view and answers `Content-Disposition: inline`, `no-store`. It is served by the app, not by storage, because Supabase storage links are sandboxed and a browser's PDF viewer will not show them in a frame. Download is a separate button (60-second signed link, `download` set). A signer's first open (viewer or download) is what unlocks signing. **A Word (DOCX) file is rebuilt as safe plain HTML on our server** (`documents/docx.ts`: `docxToPreviewBody`, rebuilt from an allowlist of structure tags with every attribute removed, pictures, links and scripts dropped, served in a CSP `sandbox` with no scripts or network), so resumes and stored documents can be read without downloading. The old DOC format cannot be shown and stays download-only. Any new place that shows a stored file should reuse this pattern.
- **Written in ELEVATE, initials on each page** (migration 0077, `compose.ts`, `compose-editor.tsx`, `initials-stepper.tsx`): on `/signing/new` HR can **write or paste** the document in an editor instead of uploading a PDF (toolbar for bold, italic, headings, lists, quote; preview; paste from Word or Google Docs is converted to Markdown by `html-to-markdown.ts`). The Markdown (60,000 characters at most, `MAX_COMPOSED_CHARS`) is rendered to a PDF with the same renderer as offer letters (`renderComposedPdf`; Word punctuation is normalized by `normalizeTypography`, other alphabets print as "?" and the editor warns), and from there it is an **ordinary envelope**: the PDF is the original, fingerprinted and never edited. A draft is not re-editable: discard it and write again. **"Each person initials every page"** (`esign_envelopes.initial_each_page`, ELEVATE users only; refused with an outside signer): the signer reads the document page by page in `InitialsStepper`, types initials (2 to 5 letters) and confirms each page; `recordSignature` refuses unless the initials are valid and **every page number 1..N** was confirmed, stores `initials_text` and `initialed_pages`, and the seal stamps the initials at the foot of every original page of the sealed copy (one slot per signer) and lists them on the certificate. Outside signers (offers) never get this step.
- **Verify** hashes the PDF in the browser and sends only the fingerprint (rate limit `verify`): the answer is match or no match, the seal date and the reference, nothing about who signed. A one-byte change fails.
- Wording says "agreement" and "signature" (1099 contractors); the consent text and RA 8792 fit should be reviewed by counsel. Notarized documents still need wet ink.
- Tests: `src/modules/signing/signing.test.ts` (pure), `tests/integration/signing.test.ts`, `tests/authz/signing-actions.test.ts`, `tests/e2e/signing.spec.ts`.

## Offers and hiring (Phase 3.3)

- `src/modules/offers/`, tables `talent.offer_templates`, `offers`, `onboarding_cases`. **Templates** (HR, `/recruiting/offer-templates`) are Markdown-style letters with fixed `{{merge_fields}}` (`merge.ts`: candidate_name, offer_date, expires_on, role_title, start_date, client_name, pay_note); an unknown or unclosed field cannot be saved. Fields are filled **after** parsing (a value can never become formatting or a link) and the applicant's name is stripped of formatting characters. **Pay is a free-text note only**: no rate, currency or hours are stored, calculated or exported. Letters say "independent contractor" (counsel to review the sample wording). The PDF is drawn with `@react-pdf/renderer` (`offer-pdf.tsx`, standard Helvetica, non-Latin text becomes "?"; it is a dependency approved by the owner and builds under `next build`).
- **Making an offer** (`makeOffer`; HR, Super Admin, recruiters; the applicant must be at the **Offer** stage; one live offer at a time): renders the letter, stores a **snapshot** of the final text in `offers.rendered_body` (editing the template later never changes a sent letter), and calls signing's `createEnvelope` with the applicant as an **outside signer** and an optional ELEVATE countersigner (signs after the applicant). **An offer's status is its envelope's status** (`offerStatus`: no envelope or draft = draft, out = sent, completed = signed, declined, expired, voided = withdrawn): no copies to keep in step. Offers can be saved as drafts, sent later, withdrawn (voids the envelope) and resent.
- **Outside signers** (`signing/external*.ts`, `esign_signers.user_id` is null, `external_email`/`external_name` set; exactly one of the two kinds): the applicant gets an emailed link `/sign/<token>` (a 256-bit random token, stored only as a SHA-256 hash; a resend replaces it), then must request a **6-digit code** emailed to the same address (valid 15 minutes, five wrong tries lock it, a new one needs a request, at most five codes an hour per person, all hashed) before they can read or sign. The right code starts a **two-hour session**: a random value in an httpOnly cookie (`elevate_sign_session`), only its hash stored. They read the PDF in the page and sign through `recordSignature()` (`signing/service.ts`), **the same rules as an ELEVATE user** (must be their turn, must have opened the document, consent, typed or drawn). The certificate records "email link and one-time code" as how they proved who they are, plus time and IP. Link and code emails go **straight out** (never queued, never BCC'd, never logged) and the link email carries no role, pay or client. After sealing they get a "signed copy ready" email; **the link they were using keeps working** (`previous_token_hash`) to open the signed copy, and links stay reachable for 30 days after a document ends. Public routes: `/sign/[token]` and `/api/sign/[token]/{code,verify,document,sign,decline}` (rate limits `signCode`, `signVerify`, `signPublic`; `/sign` is a public prefix, `/signing` is not). The immutability trigger on signed signer rows now allows only the link, code and session columns to change.
- **Hiring** (`hireCandidate`; **HR and Super Admin only**): needs a signed offer, or a written reason (stored in `onboarding_cases.hired_without_offer_reason`, audited). In one transaction: `createEmployeeRecord()` (`people/create.ts`, shared with "Add person": contractor, status onboarding, links an existing account with the same email), `markHired()` (`recruiting/service.ts`: stage, history, audit), an **onboarding case** (`talent.onboarding_cases`, which Phase 3.4 builds on), and an invitation via `ensureInvitation()` (`settings/invite.ts`, shared with Settings > Invitations) when they have no account; the invitation email goes out after the commit (`emailed: false` tells HR to share the Accept an invite steps). A work email that already exists rolls everything back. Retention never purges a hired person. The resume and the signed offer stay linked through the application and the onboarding case; copying them into the document vault comes with onboarding (3.4).
- Permissions: `offers.manage_templates`, `offers.hire` (HR, Super Admin), `offers.make` (plus recruiters), `offers.view` (plus a team lead on the job's hiring team). Tests: `src/modules/offers/merge.test.ts`, `tests/integration/offers.test.ts`, `tests/authz/offers-actions.test.ts`, `tests/e2e/offers.spec.ts` (no email service locally, so the e2e puts the applicant's link and session in the database; the emailed-code step is covered by the integration tests).

## Onboarding and offboarding (Phase 3.4)

- `src/modules/onboarding/`, tables in schema `talent`: `checklist_templates` (+ `_items`; one default per kind, one per position), `onboarding_cases`, `offboarding_cases`, `checklist_tasks`, `exit_interviews`, `certificates`. The onboarding case table moved here from offers; hiring calls `openOnboardingCase()` inside the hire transaction. With no template the built-in lists in `constants.ts` are used; changes to a template affect new cases only.
- **Tasks** have an owner (HR, the person's lead, the person), a due date counted from the start date (onboarding) or last working day (offboarding), a required flag and a check kind. `manual` tasks are ticked by hand (`completeTask`: HR any task, the person their own, the lead their own and their downline's lead tasks); every other kind is **ticked by ELEVATE** when it sees it is true (`satisfiedTasks`/`syncCase`: document uploaded, all required documents, policy acknowledged by the latest published version, account exists, agreement envelope completed, exit interview submitted, access removed). Pages and the 30-minute `checklist-sync` job record them. HR can skip (with a reason) and reopen. `completeOnboarding` (HR) needs every required task closed, then moves the person from onboarding to active.
- **Separation** (`executeSeparation`, hourly `offboarding-separations` job after the last working day ends in the person's own zone, or HR's "Remove access now"): `changeEmployeeStatus(... "separated")` with the end date, ends client assignments, schedule, waiting leave and extra-hours requests (approved leave and the ledger are untouched), disables the Supabase login (`accounts.ts`, `setLoginDisabler()` in tests), archives the user. Each step is saved in `offboarding_cases.steps`, so a retry continues and a second run changes nothing. It refuses while the person has active reports (HR is told); an open clock session only notifies the lead and HR. A case can be cancelled until access is removed.
- **Exit interview** is the person's own form; only HR reads the answers (`getOffboardingCase` hides them from everyone else; audit never stores them). **Certificate of engagement** (`issueCertificate`, HR): a PDF (`renderOfferPdf`) with a `CE-YYYY-XXXXXX` reference, stored in `signed-docs/certificates/`, shown inline at `/api/certificates/[id]` (HR only, each view audited). It states dates and role only.
- Final hours are a manual task linking to `/hours-review`; ELEVATE never computes pay. Assets are manual tasks until Phase 4. Retention of separated people's data is unchanged (counsel).
- Pages: `/onboarding`, `/onboarding/[id]`, `/onboarding/templates`, `/offboarding`, `/offboarding/new`, `/offboarding/[id]` (each its own menu address; lists are paged). Jobs `offboarding-separations`, `checklist-sync`, `checklist-reminders` are in the health registry.
- Tests: `src/modules/onboarding/onboarding.test.ts` (pure), `tests/authz/onboarding-actions.test.ts`, `tests/integration/onboarding.test.ts`, `tests/e2e/offboarding.spec.ts`.

**Wording in Signing screens:** the person who receives a document and signs it is the **signee** (labels, messages, notices). "Signer" is kept for ERS people who countersign, and in code, tables and JSON keys (`esign_signers`, `signers`), which do not change.

**Starting onboarding for a person added directly** (`startOnboarding`, permission `onboarding.start`, HR and Super Admin; migration 0078 makes `onboarding_cases.application_id` optional): a person created under People (not hired through Recruiting) has no case, so nothing shows in progress. HR opens one on **Onboarding > Start onboarding for someone already added** (person and start date). It uses the position template or the default list, once per person, and stores the reason "Added directly under People".

**ELITE letterhead and ready-made documents** (`letterhead-pdf.tsx`, `brand-logo.ts`, `builtin-templates.ts`): documents written in ELEVATE are drawn in the NDA design: the logo centered at the top with room above it, the **title centered and bold**, one-inch side margins, a faint logo watermark and a footer ("ELITE RESOURCE SERVICES", page x of y) on every page. HR can start from a ready-made document on "Write or paste it here" (a plain list in `builtin-templates.ts`, copied into the editor and still editable). First one: **Personal Time Off (PTO) Policy**, from HR's PDF. Add another by adding an entry to that list.

**Adding signees by group** (`findSignees`, `listSigneeGroups`, `resolveSigneeGroup` in `queries.ts`; the form posts with `individual=true`): on "Who signs", HR can add **everyone**, **a team** or **a client's current assignees** (people with an ELEVATE account who have not left; resolved on the server). Past 10 people (or when ticked) each person signs **their own copy**: one envelope per person (own signature, own sealed file), sent in batches of 10 per request so each stays inside the time limit; a failed batch reports how many were sent so nobody gets two. No signing order in that mode.

**Details filled in from each person's record** (`merge.ts`, `compose.ts`: `loadSigneeValues`, `assertSigneeValues`, `renderForSignee`): in a document written in ELEVATE, `{{contractor_name}}`, `{{contractor_address}}`, `{{role_title}}`, `{{start_date}}` and `{{reporting_line}}` are replaced with the signee's details when it is sent (insert buttons under the editor; the preview shows them as labels). A document that uses them goes out as **each person's own copy** (one signee, or "Each person signs their own copy"). Before anything is created, every person is checked (`?check=1` requests, which do not count against the upload limit): a missing address or manager stops the whole send and names who and what. Values are cleaned (no braces or formatting characters), so a value can never add fields or formatting. The agreement date is **not** a field: the original cannot change after sending, so the date is the signing date on the signature page and certificate; the text should say so.

**Contractor Handbook and NDA as ready-made documents** (`builtin-contracts.ts`, from HR's clean text): the handbook (11 sections plus the acknowledgment) and the NDA, which fills in the Recipient's name and address from their record and is **countersigned by the Company**: on per-person copies HR can pick a countersigner (role defaults to "Head of People Operations" for the NDA) who signs **after each person**, on every copy. The "Contractor Name / Signature / Date" and "By / Name / Title / Date" lines are not in the text (the signature page covers them), and the agreement date is the date of the last signature. Parts HR must still write are marked `[[like this]]` (none in the ready-made documents now: the NDA carries the registered address, 8 The Green, Suite R, Dover, Delaware 19901): the editor warns and the send is refused while any remain. The Independent Contractor Agreement is not built yet: it needs fields the signee types in (bank details) and typed-in terms (rate, duties, schedule).

**Independent Contractor Agreement, typed-in terms and details typed while signing** (migration 0079; `builtin-contracts.ts`, `merge.ts` `SEND_FIELDS`, `constants.ts` `SIGNEE_DETAIL_FIELDS`): the agreement is a ready-made document. **HR types the terms when sending** (`{{monthly_rate}}`, `{{payment_frequency}}`, `{{duties}}`, `{{work_schedule}}`, `{{courts_location}}`; inputs appear under the editor for the fields the text uses; pay stays free text) and the rest fills from the record (name, address, role, start date, manager). The **contractor types their bank details while signing** (`esign_envelopes.signee_details`, a fixed list of keys; `esign_signers.fills_details` is true for the person, not the Company countersigner): each is checked on the server, the set is stored as JSON **encrypted with the field key** (context `esign_signer_details:<signer id>`, `details_enc`), the event log records only the keys, never the values, and the sealed copy prints them under that person's signature (the bucket is private; HR views are audited). They are never written to `core.employee_sensitive`; if payout details should also feed the person's Payout record, that is a separate step. The peso sign is printed as "PHP" (the standard PDF font cannot draw it).

**Who can open a signed copy with personal details; send limits; the "Before you send" note:** a signed copy of an envelope that collected details while signing (`signee_details` not empty: the Independent Contractor Agreement's bank information) can be opened only by the **contractor who typed them** (`fills_details`), **HR and Super Admin** (`signing.manage`); the Company countersigner and anyone else on the envelope get a plain notice instead (`openSigningDocument`, `canOpenSealed` on the page). Sealing reads those details, so it writes a `sensitive.view` audit entry (field names only, never values). **Send limits:** a send to many people uses its own allowances, `signSend` (60 requests per 10 minutes, each is a batch of 10) and `signCheck` (120) instead of `upload`. A batch checks and fingerprints a shared PDF once (`inspectPdf`, `pdfInfo`) and flushes the email queue once after the loop (`emailNow: false`). The "Before you send" instructions beside the editor are `send-instructions.tsx` (fixed text; update it when the send form changes).

**Test marks, archive and permanent delete of test documents** (migration 0080; `setEnvelopeTest`, `archiveEnvelope`, `deleteTestEnvelope`): `esign_envelopes.is_test` (ticked on the send form, or set later; HR and Super Admin; audited as `signing.mark_test`) shows a "Test" badge everywhere. **Archive** (`archived_at`, HR and Super Admin; not while a document is out for signature: void it first) hides it from the lists, including the signee's "To sign" list, and can be undone; the "All documents" tab has Active, Test documents and Archived views. **Permanent delete** (`signing.delete_test`, **Super Admin only**, with a reason) works only on a document marked as a test and removes its files, signed copy, signers and log in one transaction; it is refused when an offer or an onboarding task uses the envelope. The database enforces it: the guards (`esign_envelope_guard`, `esign_events_guard`, `esign_signer_guard`) refuse to delete anything that is neither a draft nor a test, and the audit log keeps who deleted what and why (title, status, signee count, reason; never content). The signer guard now also freezes `initials_text`, `initialed_pages`, `fills_details` and `details_enc` after signing (the earlier guard missed them). Marking a real document as a test is the one way to make it deletable: it is audited, and only a Super Admin can then delete it.

## Emails go out at once

Interview invitations (to the applicant and the interviewers' calendar emails), cancellations, rejections and "we received your application" are queued and then sent right away by `sendRecruitingEmailsNow()` (`recruiting/immediate.ts`), best effort after the transaction commits. If no sender is configured, a daily cap is used up or the send fails, they stay queued and the 30-minute jobs send them.

## Signed documents filed in the signers' Documents

When an envelope is sealed (and by the 30-minute sweep for older ones, 50 envelopes per run), `fileSignedCopies()` (`signing/filing.ts`) files a copy of the sealed PDF as a **Signed document** in the Documents of every signer who has an ELEVATE account and a people record (`fileSystemDocument()`, migration 0087; one row per signer in `docs.system_documents`). Outside signers (an applicant signing by emailed link) have no Documents and get nothing. A document that holds details typed while signing (bank details) is filed ONLY for the contractor who typed them, never for the countersigner; HR sees it through the person's Documents like any file. The copy is made in the employee bucket, never a pointer to the signing bucket (retention for a person's documents would delete the signed evidence).

## Job feed and the WordPress plugin

`GET /api/careers/jobs` (and `/api/careers/jobs/<slug>` for one job with its Markdown description) is a public, read-only feed of the open, un-archived jobs: id, slug, title, location, pay note, posted date, the address on ELEVATE and a 300-character summary (`recruiting/public-feed.ts`; no applicant data and no internal field). It is cached by the network for 60 seconds (`s-maxage=60`), rate limited per address (`careersFeed`, which stays up if the limiter is down), and a browser on another site may read it only if its address is in `CAREERS_FEED_ALLOWED_ORIGINS` (a server, such as the WordPress plugin's own PHP, needs none). The careers pages may be framed only by this site and the sites in `CAREERS_EMBED_ORIGINS` (`frame-ancestors`, `next.config.ts`); the job page carries schema.org `JobPosting` data. The plugin is `wordpress/elevate-jobs/` (shortcode `[elevate_jobs]`; build the zip with `pnpm wordpress:zip`; install steps in its README). Applying always happens on ELEVATE (consent, resume checks, the apply rate limit), never through WordPress.
## Offer letter design and completing an onboarding

- An offer letter is drawn with the signing document design (`renderLetterheadPdf`, `signing/letterhead-pdf.tsx`): centered logo and title, watermark, one-inch margins, the ELITE footer. The template's first heading becomes the centered title (`offerLetterParts()` in `offers/merge.ts`), "Offer of Engagement" when a letter starts with text. `offer-pdf.tsx` still draws the certificate of engagement and the import reconciliation report.
- HR and Super Admin can "Complete anyway" with a reason when required tasks are open (`completeOnboarding` with `overrideReason`): the open tasks are closed as skipped with the reason, the person becomes active, and the audit entry keeps the reason and the titles that were open. They can also tick a task ELEVATE would tick itself (a policy, documents, training) by hand with a reason (`completeTask`, audited with `byHr`).

## Documents list: types, filters and All files

Each document type has a category (identity and checks, training, agreements, company, other) with its own colour and an icon per type (`documents/type-style.ts`, a type nobody planned for falls back to "Other"); the list shows a Type badge column, type filter chips with counts, a search box and Group by type or folder (`document-filters.tsx`, used by the person's tab and the Company tab). HR and Super Admin also have an **All files** tab on `/documents` (`listAllEmployeeDocuments`, `documents.view_overview`): every active employee document, paged, filtered by search and type; downloads stay on the person's own page (signed 60-second links, audited).

**Rename, restore, bulk archive and delete (HR and Super Admin only; `documents.rename/restore/delete/bulk`).** `renameDocument` changes `originalName` only; `sanitizeFileName` keeps the extension tied to the real file type and the storage path never changes. `bulkUpdateDocuments` (archive, restore, delete; up to 100 ids) runs one transaction per file, reports `failed[]` with reasons and writes one summary audit row (`document.bulk_<action>`: ids and counts, plus the HR-written reason for a delete, never file names). Delete is permanent and works on **archived files only**; it refuses a file an announcement uses (`docs.announcements.attachment_document_id`) or the system filed (`system_documents`, otherwise the sweep would file it again), removes reminders, then removes the stored file after the database change is saved (an orphan file is harmless). Checkboxes and the bulk bar (`document-bulk-bar.tsx`) are on the person's Documents tab, the Company tab and the All files tab (which has a "Show archived files only" filter so archived files can be restored or deleted).

## Deleting a job ad, erasing an application, bulk document upload

- **Delete job** (`deleteOpening`, `recruiting.delete_opening`: HR, Super Admin): a job nobody applied to is erased with its hiring-team rows; a job with applications is closed and archived instead (hidden everywhere, applications kept under the retention rules). Audit `recruiting.opening_delete`.
- **Erase application** (`deleteApplication`, `recruiting.delete_application`: Super Admin only, typed `DELETE`): for test data. Removes the application, stage history, notes, interviews, scorecards, queued applicant emails, and the applicant (with resume file and self-identification answers) when it was their only application. It opens the append-only tables the same way the retention job does (`talent.retention` set for the transaction). Refused when an offer, an onboarding case or a hire exists. Audit `recruiting.application_erase` holds ids and counts, never a name.
- **Bulk upload** (`documents/components/bulk-upload.tsx`): drag and drop or choose up to 50 files; each takes the normal three upload steps one after another and lands as the type `Unsorted` (`unsorted_employee` / `unsorted_company`, migration 0090) with the file name as its title. "Set type" / "Change type" on a row (`changeDocumentType`: the owner for their own unverified files, HR for any, `documents.manage_company` for company files) gives it its real type and asks for the expiry date or client that type needs. The `upload` rate limit is 60 per 10 minutes for this.
- **About me** (gender, pronouns, religion) is an "Edit about me" pop-up on the Personal tab, no longer a card on the page.
