# Announcements, policies and email

> Moved out of CLAUDE.md to keep that file short. These are the full working notes for this area: read them before changing it. The hard rules are repeated in CLAUDE.md's "Module notes" index.

## Announcements, policies and email (Phase 1.4)

- `src/modules/announcements/`: announcements (Markdown, audience everyone or teams, recipients frozen at posting), versioned policies (`docs.policy_versions`: a published version is frozen by a database trigger; changes are new versions), and `docs.acknowledgments` (insert-only trigger; one row per person and item/version). For policies the `id` in actions is the policy **version** id.
- **Email choices** (the weekday summary checkbox, `DigestPreference`) live on **Settings > Email notifications** (`/settings/notifications`, every signed-in person; also in the account menu), not on the announcements page. A new personal email choice goes on that page. **Email choices are opt-in (migration 0071): everyone starts unticked; no row means no email.**
- **Pictures and files** (`docs.content_files`, migration 0052, `announcements/content-files.ts`, routes `/api/content/files` (upload) and `/api/content/files/[id]` (serve), editor `content-files-editor.tsx`): an announcement or a policy version can carry pictures (shown inside the text as a line of its own, `![description](file:<id>)`, parsed only by `parseRichMarkdown`, so offers and other text never show them and an outside address never becomes an image) and PDF or Word files (downloads under the text, real type judged by `sniffFileKind`, no macros, 10 MB). The browser re-encodes a picture to a JPEG of at most 1600 px (so camera and location details never leave the device) and the server checks and cleans it again (`cleanJpeg`, 1.5 MB). A file is uploaded first (pending, owned by the author, private to them) and bound when the item is saved (`syncContentFiles`: max 12; pictures the text does not point at are dropped; a new policy draft starts with a copy of the earlier version's rows, sharing the stored file; the stored file is deleted only when no row uses it); pending files nobody saved are removed after a day by the daily cleanup job. **The files of a published policy version are frozen by a database trigger**, like the version; an announcement's files cannot change once someone has acknowledged it (same rule as its text). Stored in `company-docs/content/`, served to people who can read the item (an announcement's audience; a published policy to everyone; a draft or pending file only to HR or its author). **Documents never pass through a server request body** (the host limits it to about 4.5 MB): the editor uses `upload-actions.ts` (`requestAnnouncementFileUpload` -> browser uploads with the one-time token -> `finalizeAnnouncementFileUpload`, which reads the stored file and judges it by its bytes; a row is unusable while `sha256 = ''`), and a download is a 307 to a 60-second signed storage link that saves it under its own name (audited as `content.file_view`, the upload as `content.file_add`). Only pictures (1.5 MB) still use `POST /api/content/files`. **Failed storage removals are retried:** every path whose last row goes is queued in `docs.storage_deletions` (migration 0102, same transaction as the delete); `deleteUnusedPaths` clears an entry only after storage confirms the removal (or the path is in use again, since policy versions share files), and the daily cleanup job calls `retryStorageDeletions`. Queue a path with `queueStorageDeletion(tx, paths)` whenever you delete `content_files` rows.
- **Video on an announcement** (`content_files.kind = 'video'`, migration 0101, `content-files.ts` request/finalize/cancel, `video-actions.ts`, bucket `announcement-videos`, `ContentVideo` in `content-file-list.tsx`): HR and Super Admin (`announcements.manage`) add **one MP4 or WebM of up to 100 MB** to an **announcement** (never a policy). It does not pass through the Next.js server (Vercel limits a request body to a few MB): `requestAnnouncementVideoUpload` (server picks `videos/<uuid>.mp4`, inserts a row with `sha256 = ''` that cannot be bound or played yet, returns a one-time token) -> the browser sends it with `uploadToSignedUrl` -> `finalizeAnnouncementVideoUpload` reads only the first 64 bytes and the size (`DocumentStorage.head`), judges the type with `sniffVideoKind` (MP4 `ftyp` with an ordinary brand, WebM EBML with doctype `webm`; QuickTime/HEIC/Matroska refused) and a failing file is deleted. For a video `sha256` is the hash of the first bytes only. Playback: `GET /api/content/files/<id>` checks the same audience as any content file, audits `content.video_view` once per viewing (not per Range request) and answers a 307 to a 5-minute signed storage link (storage serves Range, so seeking works). It shows above the text on the announcement page and in the sign-in pop-up. Same freeze as pictures: once someone has acknowledged, the video cannot change. Unsaved uploads are purged after a day (`purgeOrphanContentFiles`, `deleteUnusedPaths` picks the bucket by the `videos/` prefix). The editor warns not to show client or patient screens. There is no captions field: write a transcript in the announcement text.
- **Write/Preview:** every Markdown text box for policies and announcements is `MarkdownField` (`src/components/markdown-field.tsx`): a Write/Preview toggle that renders with the same `Markdown` component and frame as the published page, plus a character count. Use it for any new Markdown input.
- **Removing a policy:** `archivePolicy` archives (never erases) a policy that was never published and has kind `general`; the built-in privacy notice and monitoring policy, and anything published, cannot be removed. `createPolicy` always makes kind `general`: the sign-in gate and the Jibble switch read the built-in ones by kind, so their text is edited in those policies, not in new ones.
- Markdown goes through `src/lib/markdown.ts` into React elements, never an HTML string. Do not add `dangerouslySetInnerHTML` for user text.
- The seeded privacy notice and monitoring policy are DRAFT placeholders; publishing refuses text containing "DRAFT PLACEHOLDER". Phase 1.5 and the Jibble mirror gate read them by `kind`.
- **Email:** everything is queued in `ops.email_queue` and sent by the `email-sender` job under a rolling 24-hour budget (`EMAIL_DAILY_BUDGET`, default 250 on Brevo's free 300 a day, 90 on Resend's free 100; `EMAIL_PROVIDER` picks the sender, Brevo over SMTP by default once `BREVO_SMTP_KEY` is set). Acknowledgment emails go first, then the weekday 8:00 AM Manila digest. Bodies carry counts and a link only. With no provider key (`BREVO_SMTP_LOGIN`+`BREVO_SMTP_KEY`, or `RESEND_API_KEY`) and `EMAIL_FROM` nothing is sent and the queue waits. Tests use `setEmailSender()`.
- Pass `Date` values to drizzle comparison helpers (`lt`, `gte`), not raw `sql` fragments: raw fragments skip the driver's date encoding.
- Production go-live: Supabase's built-in auth email is heavily rate-limited; configure custom SMTP (Brevo or Resend; use the same Brevo SMTP login and key) when the Pro project is created.

## Privacy notice and "My data" (Phase 1.5)

- **Gate:** `(app)/layout.tsx` calls `getPrivacyGate()` (`src/modules/privacy/queries.ts`). Until the current published version of the policy with `kind = 'privacy_notice'` is accepted, the layout renders only the acceptance screen. No published notice = no gate; a failure loading it fails open. It is a page-level gate; actions still authorize normally. Acceptance is the same insert-only `docs.acknowledgments` row as any policy (accounts with no people record may accept it too). The privacy notice and monitoring policy always get `requires_ack = true` when published.
- **No version number is shown for the privacy notice or the monitoring policy** (`hidesVersion(kind)` in `announcements/constants.ts`): the policy page, the policy list, the editor ("Draft", "Publish update"), the sign-in screen, the publish notification and My data say "published <date>" instead. The integer version is still stored and acknowledgments are still recorded per version; other policies keep "Version N".
- **Publishing the privacy notice is permanent** in a database (versions are frozen), and it stops everyone at the screen. Never publish one against a shared dev database you still use for e2e: `tests/e2e/privacy-gate.spec.ts` runs in its own Playwright project after the others and archives the policy at the end (`update docs.policies set archived_at = now()` switches the gate off). If that test crashes, run that SQL.
- **My data** (`/my-data`): `collectMyData()` in `privacy/service.ts` reads only the signed-in account's own rows, returns sensitive fields as stored masks (never decrypts), and names no other person in the activity list. JSON and PDF (`pdf-lib`, Helvetica, non-Latin text becomes "?") come from `exportMyData`, rate-limited and audited as `mydata.export`.
- **Data rights requests** reuse `core.change_requests` with category `data_rights` (correct, delete, other). HR is notified; approving applies nothing automatically, because deletion is a retention and counsel decision.
- After adding a migration, run `pnpm db:migrate` against the local database before `pnpm test:e2e`: the integration tests build their own database, so they will not reveal a missing local migration.

## Sign-in pop-up queue

HR (`announcements.manage_popups`: HR and Super Admin) queues an announcement or a published policy as a pop-up from its own page ("Show as a pop-up", a date) and orders the line under Announcements, Pop-up queue. Tables `docs.popups` (the queue, apart from the frozen item so a published policy can still be queued; migration 0084) and `docs.popup_dismissals` (insert-only; for a policy, per version). `listMyPopups()` (popup-queries.ts) returns what is due for the signed-in person: announcements only for the people they were addressed to, policies for every active person (general policies only; the privacy notice and monitoring policy have their own screens), in line order, at most 6 at a time. The layout renders the text on the server and `PopupQueue` (client) shows them one at a time before the page, with the list frozen at mount (acknowledging refreshes page data and a shrinking list would skip one). An item that needs acknowledgment cannot be closed (no X, Escape or outside click): `acknowledge` is the only way on; any other is closed with `dismissPopup` and never returns (a new policy version does). The quick tour starts only after the line is empty.

## Removing announcements and policies

- **Archive** (HR, Super Admin; `announcements.manage`): any announcement, and any general policy, published or not. It leaves the lists, the acknowledgment banner, reminders and the pop-up queue; versions and recorded acknowledgments are kept. The privacy notice and monitoring policy can never be removed.
- **Delete** (`announcements.delete`: HR, Super Admin): an announcement only, and only while nobody has acknowledged it (acknowledgments are insert-only, so those are archived instead). It removes the recipients, team choices, pictures and files, reminders, pop-up and dismissals with it; the audit entry holds the id and counts, never the text. There is no delete for policies.
