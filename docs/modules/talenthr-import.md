# TalentHR import and go-live

> Moved out of CLAUDE.md to keep that file short. These are the full working notes for this area: read them before changing it. The hard rules are repeated in CLAUDE.md's "Module notes" index.

## TalentHR import (Phase 5, part 1)

- `src/modules/imports/`, tables `ops.import_batches` and `ops.import_rows` (migration 0040, RLS on). Page: **Settings > Import from TalentHR** (`/settings/import`, `/settings/import/[id]`); permission `imports.manage` (HR and Super Admin only). **Real exports are never put in the repo, tests or a development database**: the real dry runs happen in the production system (the quarantine), and every test uses the invented files in `tests/fixtures/talenthr-export.ts` (same 45 columns as the real export).
- **Steps:** upload the CSV (route `/api/imports/stage`: 2 MB, 2,000 rows, rate limit `upload`) -> choose where each column goes and the date format (defaults for TalentHR's columns in `mapping.ts`; the choice is saved on the batch) -> the file is read into a **preview batch** (`stageBatch`: nothing is created) -> HR reads the rows (new, changed, unchanged, errors, warnings, paged) -> **commit** (`commitBatch`, one transaction; no emails, no accounts) -> reconciliation and sign-off. Rows with errors block the commit unless HR ticks "skip them". A row's issues name the field and the problem, never the value.
- **Quarantine:** each staged row is the normalized person **encrypted** with the field key (context `import_row:<batch>:<row>`); outcome, field names and issues are the only plain columns. The payload is wiped when the batch is committed or discarded, and a daily job (`import-purge`, 3:40 AM Phoenix, in the health registry) discards previews older than 14 days.
- **Defaults:** workers are imported as 1099 contractors. "Terminated" (or any termination date) means separated with that last working day; a future start date means onboarding. Department becomes a team and Job Title a position (both created if missing; new teams sit under a department called "Imported from TalentHR"). Pay rate and currency go to the encrypted sensitive fields (HR only, ELEVATE never computes pay). Birth date, civil status, phone, address, country (names to codes), emergency contact (needs name and a valid phone) map to the built-in fields. Location, Division, shirt size, onboarding date and the status text become **HR-only custom fields**. **Left out by default:** gender, citizenship, avatar, free-text "Compensation and Benefits", free-text notes, pay schedule, overtime, approvers: HR can map a column to a custom field in the screen, but custom fields are never for sensitive data.
- **Matching and re-imports:** people are matched by **work email** (case-insensitive), so a second dry run updates the same people ("changed" lists field names, "unchanged" changes nothing) and restores anyone a rollback archived. A person who **already has an ELEVATE account** keeps their status and dates: the file never changes them (a warning says so). Supervisors are linked through the TalentHR ID within the file and applied last through `applyReporting()` (dated, no loops); a refusal or a supervisor who is terminated or not in the file is a warning on that row, not a failure.
- **Rollback** (`rollbackBatch`): people the batch CREATED are **archived, never deleted**, unless they have signed in or have activity (clock events, leave, schedules, equipment); those are kept and counted. Changes the batch made to people who already existed are not undone. The ledger, history and audit log are append-only, so deleting is not possible by design.
- **Reconciliation** (`getReconciliation`, PDF at `/api/imports/[id]/reconciliation`, counts only): file versus ELEVATE for total people, current people, terminated people, skipped rows and managers that could not be set; HR signs off (audited `import.signoff`). Leave and documents are compared once pulled from the API (part 2).
- **Dates:** the screen asks for the format (month/day/year is TalentHR's), impossible dates are errors, and a bad birth date is only a warning (left empty).
- Tests: `src/modules/imports/imports.test.ts` (CSV, mapping, dates, countries, normalizing), `tests/authz/imports-actions.test.ts`, `tests/integration/imports.test.ts`, `tests/e2e/import.spec.ts`.

## TalentHR API pull and go-live (Phase 5, part 2)

- **API pull** (`src/modules/imports/pull.ts`, `talenthr-client.ts`, script `pnpm talenthr:pull`, tables `ops.import_pulls` and `import_pull_items`, migration 0041). TalentHR's API is a Postman-documented REST API at `https://pubapi.talenthr.io/v1` with HTTP basic auth; the client only ever sends GET requests, keeps under the 2,000 a minute limit, retries 429 and 5xx, and sends credentials only to TalentHR's own host (a file link on another host is fetched without them). The key is `TALENTHR_API_KEY` in the git-ignored `apps/elevate/.env.talenthr.local`, never in chat or the repo; `--probe` finds out whether it works as the user name or the password.
- **What it does:** for each TalentHR person whose work email matches a person in ELEVATE (so import the people CSV first): their **documents** are downloaded (10 MB, real type checked by bytes, JPG/PNG/PDF/DOCX only) and saved as real documents of the person under the document type "Imported from TalentHR" (private `employee-docs` bucket; a file already there, by SHA-256, is a duplicate); their **time-off budgets and requests** and the company's **jobs and applicants** are kept as **encrypted archives** (`import_pull_items.payload_enc`, readable only through `readArchive`). Skipped or failed files carry a short reason code (too_large, type_not_allowed, download_failed), never a name.
- **Excel upload:** the import screen also takes an `.xlsx` export (`xlsx.ts`, library `read-excel-file`, dependency approved by the owner; `write-excel-file` is a dev dependency used only to build invented test files). Only the first sheet is read, through the same table checks and mapping as a CSV; date cells become ISO dates. Before a spreadsheet (a zip) is opened its table of contents is read and a file that would unpack to more than 40 MB or 200 entries is refused.
- **Active applicants are loaded into recruiting** (`applicants.ts` pure rules, `applicants-pull.ts`, `recruiting/service.ts` `createImportedOpening` and `importApplication`; migration 0043 adds `import_pull_items.local_id` and the kinds `opening` and `application`). For each TalentHR job with at least one **active** applicant (a live application, not disqualified, with a usable email, whose step is not an ending such as hired, rejected, withdrawn, declined or talent pool): a **closed** job opening is created (HR reopens one to use it; no acknowledgment or rejection emails are enabled), each applicant becomes a candidate (an existing candidate with the same email keeps their own details) and an application at the nearest stage (`stageForStep`: offer, interview, assessment, screening, else applied), with the stage history noting the import, the application date and cover note kept, and the **resume** saved when TalentHR gives a PDF or DOCX up to 4 MB. Candidates carry the notice version `talenthr-import`. Nobody is emailed. Recruiters' internal notes in TalentHR are not imported. Closed, rejected and hired applicants stay only in the encrypted archive. `--no-applicants` skips it, and `--only` skips it too. Repeat runs skip what was loaded.
- **Leave is not loaded.** Prize days are rare at ERS (and the prize is sometimes cash or a coupon), so TalentHR balances are **not** written as opening-balance ledger rows and the screens do not feature them; the history is only archived. If HR ever wants specific balances, that is a small separate step to add.
- **Safety:** `talenthr:pull` refuses to run unless `ELEVATE_ENV=production`, needs `--as <HR or Super Admin email>`, supports `--dry-run` (counts only, writes nothing) and `--only a@x.com,b@x.com`, and is safe to repeat (items already imported are skipped; a skipped or failed one is replaced when retried). Every run is audited (`import.pull`, counts only). Tests use a fake TalentHR (`tests/integration/imports-pull.test.ts`); the real API is never called from tests.
- **Reconciliation** now also compares the documents TalentHR holds for the batch's people with those imported (and counts people with a document that was not imported); leave histories archived are shown as a count.
- **Go-live checklist** (`/settings/go-live`, `imports.manage`, table `ops.golive_items`, migration 0042): automatic rows (required production settings present by NAME only, privacy notice and monitoring policy published with real text, at least two Safe Voice handlers, a signed-off reconciliation, how many people have accounts) and manual steps HR ticks (domain and DNS, a backup restore test, error alerts, sign-in emails, sending domain, counsel's read, pilot team, invitations in waves, help for HR, the two-week parallel run, archive and cancel TalentHR). The settings check describes the deployment you are looking at, so open it on the live site.
- Tests: `src/modules/imports/golive.test.ts`, `tests/integration/imports-pull.test.ts`, `tests/e2e/go-live.spec.ts`, and the import authz test covers the checklist action and query.
