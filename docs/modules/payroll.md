# Payroll

Design: `docs/superpowers/specs/2026-11-04-payroll-design.md`. Plan: `docs/superpowers/plans/`. Real names and pay figures never enter the repo, tests or a development database. Code: `apps/elevate/src/modules/payroll/`. Every label comes from `constants.ts`.

## Round 3 (2026-11-12; overrides anything older below)

Owner decisions, in the order they were built:

- **Paying (`payroll.export`, `payroll.mark_paid`) is for Preparers AND Approvers.** Nobody marks their own payment (unchanged). An Approver who holds `mark_paid` also reads the Remitly references, like a Preparer.
- **The Remitly list carries payout details: Bank, Account name, Account number.** For a REAL run they are decrypted in full (`payments.ts` `payoutDetailsFor`, each value bound to its person with `sensitiveContext`), after `authorize()`, with one `sensitive.view` audit row per download (the three field names and how many people, never a value). For a TEST run only the masks stored at write time are used (nothing is decrypted) and every row says "TEST - do not pay". A person with any of the three parts missing gets blank cells (the page says how many); a value that can't be decrypted refuses the whole file. **This is an owner-approved exception to "only Super Admin, HR Admin and the person decrypt bank details"** (CLAUDE.md records it). The privacy notice must say that people with payroll access read payout details to pay them, and must be published before real data goes live.

- **Statements are released, not automatic (migration 0133, `payroll.pay_run_releases`).** A person sees their contractor payment statement only when the run is REAL and has a release row; approval, payment and a test run alone never make one visible (`payslip-queries.ts`: `listMyPayslips`, `countMyPayslips`, `getMyPayslip` join the release). `releaseStatements` (`statements.ts` `releaseRun`, permission `payroll.release_statements`, Preparers and Approvers (owner decision 2026-11-12: the Preparer may release too)) works on an approved or paid real run, once, never undone: it refuses a test run, an unapproved run, a second release and a run with an unreadable line; it freezes the signatory, writes the release row (append-only trigger), one notice per linked person (no amount, name or period), an audit row (`{ people }`) and the change-log row `statements_released`. The "statement ready" notice moved from the last payment to the release. A statement for a run released before it is paid has no "Paid on" line.
- **The payroll team's Statements pages.** `/payroll/statements` (runs, release state), `/payroll/statements/[runId]` (every person, View, Download, Download all as one merged PDF, the release button) and `/payroll/statements/[runId]/[employeeId]` (on-screen statement). Routes `/api/payroll/statements/[runId]` and `/[employeeId]`. All need `payroll.view` (every level), are rate-limited, never cached, and write one `sensitive.view` audit row per view (a field name and a count, never an amount or a name). A TEST run's statements can be opened and downloaded to check them (stamped TEST, file name ends -TEST) but never released and never visible to a contractor. One shared builder (`buildStatement`) makes both the contractor's and the team's statement so they are identical.

- **The statement fills in its own certification block.** "Prepared by" is the person who sent the run for review (else who created it), "Authorized by" is the Approver who approved it, and "Date" is the day they approved it (company zone), all read from the run when the statement is built (`buildStatement`: `pay_runs.submitted_by`/`created_by`, the newest `approved` row of `pay_approvals`; names from the people record, else the account's email). A signatory set in Settings still shows under "Authorized by" with their picture, title and signing date; with none set, the Approver's name and approval date show instead of "Not signed". The contractor's own signature line stays blank for the contractor.

## Test runs (2026-11-12, migration 0132; overrides anything older below)

The team is still rehearsing pay cycles, so a run can be a **test run** (`pay_runs.is_test`) and a test run can be **archived** (`archived_at`, `archived_by`). Nothing is ever deleted: a pay run still cannot be removed (the guard trigger refuses it).

- **Who:** `payroll.manage_test_runs`, Preparer and Approver (not a viewer, not a role). Every step asks for a reason, kept in the encrypted change history (`run_marked_test`, `run_marked_real`, `run_archived`, `run_restored`); the audit rows hold ids and the status only.
- **Marking:** a run can be marked as a test until it is paid (draft, in review, approved). A paid or cancelled run can never be marked, so a real payout cannot be hidden. A test run is made real again only while it is a draft and only if no other real run has its period. A new run can be created as a test run (`createPayRun({ test: true })`).
- **Periods:** the period uniqueness (`pay_runs_period_idx`) and the overlap check apply to real runs only, so a test run may repeat a period that already has a run, any number of times. The way to repeat a real cycle: mark the old run as a test run, archive it, create the new run.
- **Archiving:** only a test run, in any status (paid included). The trigger allows an archive or restore to change nothing else about the run, and refuses `archived_at` on a real run even from SQL. An archived run leaves the runs list (a link shows them), cannot be invoiced, and is skipped by the "net changed" and correction lookups.
- **Kept apart:** the "net changed" comparison and the runs an adjustment can correct only look at runs of the same kind (test with test, real with real). A test run never reaches a person: no "your statement is ready" notice, and `/my-pay` and the statement download only read real runs (`is_test = false`).
- **A test run can cover any dates (up to 31 days), a real run only one cutoff.** `createRun` skips the one-cutoff rule for a test run (the schema still caps it at 31 days), so a rehearsal can use exactly the dates of a Jibble file, such as 1 to 9 November. A partial test run cannot be made a real run (`setRunTest` refuses it). Its base pay is still a full cutoff unless the days worked are entered as amounts.
- **Rehearsing a past cycle with real data** is a test run for the old period, filled from the real Jibble file, paid (no money moves), previewed on the Statements page (stamped TEST) and invoiced (TEST number), then archived; see the guide `rehearse-a-pay-cycle`. Real figures only in the live ELEVATE after the privacy notice is published, never in a dev database.
- **Invoices from a test run:** allowed, numbered `TEST-<year>-<counter>` in their own series (so real `INV-` numbers never skip), stored with `is_test`, and stamped TEST on the page and the PDF.

## Round 2 of 2026-11-12 (overtime, notes, draft people, Jibble import, invoices; overrides anything older below)

Spec: `docs/superpowers/specs/2026-11-12-payroll-timesheet-invoices.md`.

- **Overtime pays from the first run.** A blank OT setting means the **standard** percent (`DEFAULT_OT_BP` in `calculate.ts`: regular 125%, rest day 130%, rest day past 8 hours 169%), applied in `snapshotOf`; a filled setting wins. OT is the person's own hourly rate x the percent, so it differs per person. Minute-type items accept `90`, `90m`, `1.5h`, `1h30m`, `1:30` (`parseDuration`); a bare number is minutes; the Amounts window has an hours/minutes choice; values read back as `1 h 30 min`.
- **Checks are notes.** `BLOCKING_CHECKS` is only `unreadable_line`. Everything else (missing OT rate, negative pay, part cutoff over a full one, unassigned suggestion, own line unchecked, out-of-date lines, unapproved days...) is a note; the Approver decides. Approval still refuses an Approver's own unchecked line and the separation of duties.
- **Draft run people (migration 0129, `pay_run_lines.excluded`).** `updateRunPeople` (`syncRunPeople`) adds people whose pay line is in force, moves a line to a newer version of its pay line (recomputed, check cleared), and excludes a line no longer in force; `removePersonFromRun` / `restorePersonToRun` do it by hand with a reason. An excluded line is kept (items are append-only) and **ignored by every reader** (worksheet, totals, hash, Remitly list, payments, payslips, suggestions, items, checks); a removed person does not make "lines out of date"; sync never re-adds a removed person.
- **Jibble timesheet import (migration 0130).** Amends rule 10 of the project rules: ELEVATE's own hours still come only from ELEVATE's time clock, and Jibble is still never read by API or mirrored into time records; but a Preparer may **upload the Jibble "Custom Timesheets" export on a draft run** to fill **suggested** amounts (client payroll hours, OT by kind, holiday pay, PTO days). Only totals per member are kept (never clock times, screenshots or location) in one encrypted payload (`payroll.timesheet_imports`, wiped on apply, discard, replacement and after 14 days; audit rows hold counts only). `jibble/xlsx.ts` is our own bounded zip/xlsx reader (Jibble writes streamed zips that `read-excel-file` cannot open); `jibble/timesheet.ts` parses the member sheets; `jibble/match.ts` pairs members with pay lines (remembered by member code in `payroll.jibble_matches`, then by name, never guessing between two lines). `confirmAllSuggestions` confirms suggestions in one step. A confirmed amount is never overwritten by a later import.
- **Client invoices** are a separate module, `docs/modules/invoices.md`. They read only client payroll hours through `clientHoursForRun` (`client-hours.ts`), never a pay figure.

## Revision of 2026-11-06 (executives and HR; read first, it overrides anything older below)

- **Pesos only.** No dollar rate (`pay_runs.usd_rate_e4` dropped, `setRunUsdRate` and the `usd_rate_changed` history action removed), no dollar allowance, no dollars column in the Remitly list (`Person,Alias,Pesos`; the executive follows Remitly's own rate). **No FTE** (`pay_lines.fte` dropped).
- **Overtime (OT)** is the payroll wording (not "extra hours"); there is **no holiday overtime**. Rates in settings: regular, rest day, rest day past 8 hours (columns `extra_holiday_bp` and `holiday_bp` dropped). **Holiday pay is always one to one** (`HOLIDAY_BP` = 10000, 100% of the hourly rate, not a setting); approved extra minutes worked on a holiday are suggested as holiday pay.
- **Leave on the run:** `sick_leave_days` (SL, **unpaid**, deducted like an absence), `bereavement_days` and `pto_days` (**paid**, shown on the statement, change no amount). Time off holds none of the three (only prize days), so they are typed, never suggested. Counsel should confirm the "PTO" wording for 1099 contractors.
- **Itemized money:** `allowance`, `reimbursement`, `bonus` and `adjustment` are any number of **named lines** per pay line and run (a name of 1 to 60 plain characters plus an amount). `pay_run_items.item_key` identifies one line (new key = new line; the same key replaces it; dismissing keeps the key; `itemKey()` in `runs.ts` keys by line, type and item key). The name travels in the encrypted item value (`ItemValue.label`), never in audit rows. Pay lines no longer carry an allowance; allowances are typed per run.
- **Formula:** gross = cutoff pay - absences - sick leave - late + OT + holiday pay + allowances; **total payable compensation** (still `net` in code) = gross + reimbursements + bonuses + adjustments - loan - other deductions.
- **Wording:** the payslip is the **Contractor Payment Statement** (menu "My payment statements", PDF `contractor-payment-statement-<period>.pdf`, number prefix `PS-`); "Net" is **Total payable compensation**. The slugs, routes (`/my-pay`) and function names keep the old words.
- Frozen lines written before this revision are read through `upgradePayload` (service.ts): the old peso allowance and adjustment become one named line each, the dollar part is not shown, the stored total is kept.

## Rules (read first)

- **No role grants payroll**, not even Super Admin. Access is `core.users.payroll_access` (`preparer`, `approver`, `viewer` or empty), chosen only by a Super Admin (`settings.set_payroll_access`, Settings > Payroll access), read fresh on every request (a removal or an archived account takes effect on the next call). **Deactivating an account clears its level** (`deactivateAccount`: audited as `user.payroll_access.update` with the level only, and an `access_changed` history row), so reactivating it never quietly restores payroll access; a Super Admin chooses again. The notice to a person whose access was removed links to `/dashboard` (they can no longer open `/payroll`).
- **Payroll pays semi-monthly cutoffs only.** `createRun` refuses any period that is not exactly one `semi_monthly` period of `pay-periods.ts` (the 1st to the 15th, or the 16th to the last day of the month), whatever the hours export's pay-period setting is, because the calculator always pays half a month. The New run dialog keeps two date boxes (prefilled with the last cutoff); the server is the check. Permission rules mark this with `payrollLevels`; the matrix rows show "no access" for every role. A Super Admin can choose people without seeing any figure.
- **Levels:** Preparer (`payroll.prepare`, `manage_rates`, `mark_paid`, `export`), Approver (`payroll.approve`), Viewer (nothing but reading). All three read runs, rates, settings and the change history (`payroll.view`, `payroll.view_history`). `payroll.view_own` is every role, own payslips only. A person has one level at a time. The Settings page warns when a level has fewer than two people.
- **Only the payroll module computes pay.** It never computes tax or government contributions and never sends money (Remitly stays manual). The hours export computes nothing.
- **Money** is `bigint` centavos (dollars in cents), never floats; amounts cross JSON as strings. Pay amounts live in the payroll tables, always encrypted (`src/lib/crypto.ts`, context bound to the row). Audit rows, notifications, email, logs and Sentry carry ids and counts, never an amount, a reference or a reason.
- Payroll copy says "overtime (OT)" and "PTO" since the 2026-11-06 revision (the schedules and extra-hours request screens keep "extra hours"). Workers are 1099 contractors: letters and copy avoid "employee" wording (counsel to confirm, see Privacy and 1099).
- Real pay data must not enter ELEVATE until the privacy notice (with the Pay wording) is published.
- The old `payRate` field in `core.employee_sensitive` is read-only reference until the parallel run ends, then removed from profiles in a separate small change. HR Admins and Super Admins who are not chosen for payroll can still see it until then.

## Data model (schema `payroll`, RLS on, no public policies)

| Table | What it holds | Rules |
|---|---|---|
| `pay_settings` | Cutoff divisor, five extra-time rates (basis points, null until set), change-warning threshold, each with an effective date | Append-only; the newest version dated on or before a date applies |
| `pay_lines` | One version of a person's line: client, alias, hours per day, FTE, payment method, last day, effective date; `amounts_enc` = monthly rate, peso allowance, dollar allowance (context `pay_line:<id>`) | Append-only; a raise or end is a new version sharing the `line_key`; the author (`created_by`) is kept |
| `pay_runs` | Period, status, dollar rate (`usd_rate_e4`), settings snapshot, creator, submitter | One live run per period (unique index; cancelled runs are left out) |
| `pay_run_lines` | Frozen copy of a line for a run: one encrypted payload with the rate, inputs and results (`pay_run_line:<id>`), flags, who confirmed it | Frozen by trigger once the run leaves draft |
| `pay_run_items` | Each entered, suggested, confirmed or dismissed amount: type, state, encrypted value and reason (`pay_run_item:<id>`), who | Append-only; the newest row per line and type wins |
| `pay_approvals` | Approvals and send-backs: run hash (`pay_approval:<id>`) and note (`pay_approval_note:<id>`), both encrypted | Append-only |
| `pay_payments` | One row per person and run: Remitly reference (encrypted, `pay_payment:<id>`), paid date, who marked it | Append-only; a correction is a newer row |
| `pay_change_log` | The change history: actor, action name, run, person, line key in the clear; old and new values and reason in one encrypted detail (`pay_change:<id>`) | Append-only by trigger, written in the same transaction as the change |
| `pay_signatory` | Versions of who signs payslips: name, title, optional signature picture (small JPEG, base64, encrypted `pay_signatory:<id>`) | Append-only by trigger; only a Super Admin writes it |
| `pay_run_signatures` | The signatory version in force when a run became paid, and the date | Append-only by trigger; written in the paying transaction; none means paid unsigned |

A person is on payroll when a `pay_lines` row is in force in the period; there is no flag. Runs are never hard-deleted and no retention job exists (counsel sets the period). Encrypted values: line amounts, run-line payloads, item values and reasons, approval hashes and notes, payment references, change details. Not encrypted: ids, dates, status, alias, hours per day, FTE, the dollar rate and the settings (these hold no personal amount).

## Calculation (`calculate.ts`, pure)

```
cutoff = monthly / 2        daily = monthly / (2 x divisor)        hourly = daily / hours per day
base   = cutoff, or days x daily + hours x hourly for a partial cutoff
gross  = base - absences - sick leave - late/undertime + OT (3 rates) + holiday pay (1:1) + allowances
total  = gross + reimbursements + bonuses + adjustments - loan - other deductions   (net in code)
```

Rates stay unrounded; each result is one exact fraction rounded once, half up, to the centavo (`divRoundHalfUp`). Totals add rounded line results. Issues come back as codes: `missing_multiplier:<key>` (minutes entered, rate not set), `missing_usd_rate` (a dollar allowance, no run rate; the checks show the run-level check instead, so it is never listed twice), `partial_exceeds_cutoff` (a partial cutoff whose base is above the full cutoff salary; exactly equal is fine), `negative_net`. Settings are snapshotted on the run, so a later change never alters an approved run.

## Draft runs and the worksheet

- `createPayRun` (`payroll.prepare`) refuses any period that overlaps a live run (advisory lock inside the transaction). It builds one run line per resolved pay line (`lines.ts`: the version in force on the period's first day is paid; a raise dated inside the period only raises `rate_change_mid_period`; a start or end inside the period is flagged). Settings are reread on create and on every change to a draft.
- Every changing action (`runs.ts`) locks the run with `select ... for update` (`lockDraftRun`) and refuses a non-draft run. Each also writes an audit row (ids and counts) and a change-log row in the same transaction.
- Items are append-only; the newest row per line and type wins. Values are stored in the smallest unit (minutes, day or hour hundredths, centavos) and validated in `items.ts` (positive whole numbers, `parseMoney`, never negative; a reduction is a loan or other deduction). A peso or dollar allowance item replaces the line allowance for that run. Client hours (an item) and FTE (on the line) never reach `calculateLine`.
- A reason is required for a loan, an other deduction, and overriding a suggestion. Saving an item recomputes that person only (all lines when settings changed) and clears the confirmation of any line whose figures changed. Reasons cannot be sidestepped: an override is judged against the newest suggestion in the whole item history for that line and type, also when removing; an allowance item below the line's own needs a reason.
- `getWorksheet` writes one `sensitive.view` audit row per call and at most one `run_viewed` change-log row per person, run and day. An unreadable line is listed, blocks review and withholds all totals; logs carry the line id and error class only.
- **Cancelling** (`cancelPayRun`, `payroll.prepare`, reason required, draft only, same run lock): status becomes `cancelled` (trigger-enforced, frozen, never deleted), the run is left out of the overlap test and of the unique period index, and is logged (`run_cancelled`, reason encrypted) and audited. This is also the fix for a wrong period or lines that changed after creation: cancel and recreate.

## Run lifecycle

`draft` -> `in_review` (`submitRun`) -> `approved` (`approveRun`) -> `paid` (every person marked paid). `sendBackRun` returns `in_review` to `draft`. Only a draft can be cancelled. Cancelled, approved and paid runs are frozen by trigger; the status trigger allows approved to paid only.

## Suggestions from approved hours

- `suggest.ts` (pure) and `suggestions.ts` read approved days through the attendance module's exports (`hours-service`), never its tables. Only days whose numbers equal their latest approval count; every other day only adds to `unapprovedDays` (a warning).
- Suggested: absent days (an `absent` flag without `on_leave`, one day each), late plus early-leave minutes, and approved extra minutes by kind: holiday (verified holiday on the person's calendar), regular (a scheduled day), and rest day (no schedule that day). Nothing changes pay until a Preparer confirms it (`confirmSuggestion`) or overrides it (reason required). A confirmed amount is never touched by a refresh; unchanged numbers add no rows; a suggestion that disappears from approved hours is dismissed with the reason "No longer in approved hours".
- A person with one line gets suggestions on it; a person with several get them **unassigned** and a Preparer chooses the line (blocking check `unassigned_suggestion`).
- **Open owner question (do not change without an answer):** on a rest day the approved extra minutes fill the lower rest-day rate first, up to 480 minutes, and only what is beyond goes to the "past 8 hours" rate. A partial approval of a long rest day therefore never reaches the higher rate. Tested in `suggest.test.ts`.

## Checks (`checks.ts`, pure; labels in `CHECK_LABELS`)

**Block** sending for review and approval: `missing_usd_rate` (run level, on **every** run with no dollar rate, even one paid in pesos only: the Remitly list always has a dollars column, and the rate can only be set while the run is a draft), `missing_multiplier`, `negative_net`, `partial_exceeds_cutoff` (days and hours worked pay more than a full cutoff, for example "15" typed for "1.5" days), `unassigned_suggestion`, `own_line_unconfirmed`, `unreadable_line`, `lines_out_of_date` (the pay lines now in force differ from what a run built now would contain; fix: cancel and recreate).

**Warn** only: `unapproved_days`, `no_payout_details` (read from stored masks, never decrypted), `new_or_leaving`, `rate_change_mid_period`, `pending_suggestions`, `large_change` (net moved more than the threshold, 10% by default, never at exactly the threshold; compared with the latest approved or paid earlier run only).

`checkInputsOf(executor, data, submitterUserId)` works the checks out relative to the person sending the run: a Preparer sees "own line" about themselves while the run is a draft, and everyone sees it about the submitter once sent (an Approver never sees "your own line" about someone else's).

## Review, approval and separation of duties

- One loader (`readRun` in `runs.ts`) decrypts a run once for the worksheet, the checks and the hash. `submitRun` (`payroll.prepare`): run lock, `recomputeRun`, then the checks inside the same transaction; refused while anything blocks or the run has no lines.
- `sendBackRun` / `approveRun` (`payroll.approve`): run lock first (of two approvals at once, the second finds the run approved), then the level is read again with the account row locked, then `approvalRefusal` (`rules.ts`, pure). Refused for anyone in `touchedBy`, for an own line unconfirmed or confirmed by the approver, and while a check blocks. There is no bypass.
- **`touchedBy`** (one SQL definition, `touchersOf` in `approval.ts`, shared with the dashboard count) is everyone who is: the run's creator or submitter; an actor in the run's change history except views, send-backs and approvals; someone who entered an item; someone who confirmed a line; **or the author (`created_by`) of any pay-line version the run pays, and of every other version of the same `line_key` with the same `effective_from` (rate authors)**. Ending a line copies the amounts into a new version with the same start, authored by whoever ended it, and that is the version the run pays; the same-start rule keeps the person who typed the amounts named. The level they hold now is never consulted. It does **not** include authors of settings changes (`pay_settings.created_by`): **open owner question**, whether someone who wrote the divisor or an extra-time rate should be barred from approving runs that use them. Deciding (send back, approve) does not count as changing the run.
- Practical consequence: if the only Approver also wrote the only rates, nobody can approve until another Approver exists or another Preparer writes new versions of those rates (which then forces cancel and recreate). Choose Approvers who do not write rates.
- **Own pay (changed 2026-11-11):** a Preparer who is also paid through payroll **may** set their own rate and enter, confirm a suggestion for or remove an amount on their own line (the change history records who did it). Nobody checks their own line (`confirmRunLine`, "Mark as checked") or marks their own payment (`assertNotOwnEmployee`, kept only for those two), and an Approver who prepared, changed or checked the run, or wrote a rate it pays, still cannot approve it. Changing a line clears its check, so another Preparer always checks the figures as they finally stand. A person with a line on the run is approved only after a different Preparer confirmed that line (`confirmRunLine`, "Mark as checked").
- The approval hash (`runHash`, SHA-256 over canonical JSON) covers every line's decrypted figures, items and confirmation, the dollar rate, the settings snapshot, the item history and the latest submission. The page gets it as `expectedHash` from the same repeatable-read snapshot as the figures; `pay_approvals.run_hash_enc` stores it only encrypted. A stale hash is refused with "This payroll changed. Reload and review it again." and writes nothing. A send-back needs a note (encrypted, shown on the draft, never in a notice).
- Notices carry a count and a link only: on submit to Approvers, on send-back and approval to Preparers. The dashboard shows Approvers a "waiting for your approval" count (`payrollRunsAwaitingApproval`, runs they did not touch), never an amount.

## Corrections

An approved run never changes. A mistake is fixed on a later run by an `adjustment` (underpaid) or an `other_deduction` (overpaid) naming the approved or paid earlier run (`correctsRunId`, kept in the item value and the change log). A reason is required, amounts stay positive, and the person must have had a line on that run. The worksheet marks a run that includes a correction.

## Payments and the Remitly list (`payments.ts`, `remitly.ts`)

- `exportRemitlyList` (`payroll.export`, rate-limited, audited, `list_exported`): only for an approved or paid run with a dollar rate set (always true for a run approved now, since a missing rate blocks review; the refusal stays as a guard); refused if a line is unreadable or negative. CSV columns: Person, Alias, Pesos, Dollars (plain decimals, cells through `csvCell`). Never account numbers.
- One row per **person** (all of a person's lines summed). Dollars = total pesos / the run's rate, rounded half up from the total. **Two different people with the same name appear as two rows** (rows are ordered by name, then id) and can be told apart only by alias or order, so check the alias column.
- `markPaid` (`payroll.mark_paid`, Preparers) records the Remitly reference (encrypted), the paid date (not in the future, not before the period starts) and the marker. A second call for the same person is a correction: a new row, the newest shows. When every person has a payment the run becomes `paid` in the same transaction (`run_paid`) and each person with an account is told "Your payslip is ready" (fixed sentence and a link). A correction after that leaves the run paid.
- **References are visible to Preparers only** (`payroll.mark_paid`). Approvers and Viewers see who marked a person and when, not the reference. Decrypting references is one `sensitive.view` audit row (a count).
- Someone with a line on the run cannot mark their own payment, and cannot check their own line; another Preparer does.

## Payslips (`payslip.ts`, `payslip-queries.ts`, `payslip-pdf.tsx`, `components/payslip-document.tsx`, `/my-pay`, `/my-pay/[runId]`, `/api/payroll/payslips/[runId]`)

- A payslip exists only for a **paid** run and only for the signed-in person's **own** lines (scoped by their people record, never by level or role; not even a Super Admin reads another person's). Someone else's run, an unpaid run and a missing run all answer 404. A person with no linked account has no payslip page and gets no notice; payroll works for them.
- **One view, two renderings.** `payslipView()` (pure) turns the person's frozen lines into plain data: a header (number, period, paid date, paid by), per pay line the earnings (base, extra hours with hours and the rate the run was made with, holiday pay, allowance, absences and late as minus) ending in **Gross pay**, the additions after gross (dollar allowance with the dollars and the rate, adjustment), the deductions (loan, other), and **Net pay**; a total when there are several lines; and the signature block. `PayslipDocument` draws it on screen (`/my-pay/[runId]`, a server component with no script, so it works without any PDF viewer; **View** on the My pay list opens it, **Download PDF** is beside it and on the page) and `renderPayslipPdf` draws the A4 PDF (`@react-pdf/renderer`, built-in Helvetica, **non-Latin characters in a name print as "?"**). The payslip holds the person's own figures only: no other person, no staff reason, no history, no bank detail, no Remitly reference. Opening the page is audited like the PDF (`sensitive.view`, run id only).
- **Who signs (the Human Resources Director).** `payroll.pay_signatory` holds versions (name, title, an optional signature picture); a **Super Admin** sets it on **Settings > Payslip signatory** (`settings.set_payroll_signatory`, no payroll level needed; audited without the name, title or picture; the payroll change history gets a `signatory_changed` row with the old and new name and title and whether a picture is on file, never the picture). Saves take an advisory lock; a payslip PDF whose picture can't be drawn is drawn without it (only the error name is logged). The picture is made into a small JPEG in the browser; the server re-checks it with the shared `cleanJpeg` (structure, 150 KB at most, no camera or location data) and keeps it encrypted (`pay_signatory:<id>`). When a run becomes **paid**, `freezeRunSignatory` (inside the paying transaction) writes `pay_run_signatures` (run, signatory version, signed-on date), so **a payslip never changes when the signatory changes later**. Nobody set yet: no row, the run is paid anyway (a signature must never hold up payment) and the payslip says **Not signed**. Both tables are append-only. Past runs paid before this existed show Not signed.
- The route is rate-limited (the 429 carries `Cache-Control: private, no-store` and nosniff like every other answer), never cached, audited (`sensitive.view`, run id only) and logged (`payslip_downloaded`). An unreadable line answers a plain 500 sentence, never a partial slip.

## Change history (`/payroll/history`, `history-queries.ts`, `history-format.ts`, `components/history-table.tsx`)

- `getPayrollHistory` needs `payroll.view_history` (level only; a Super Admin with no level gets a 404). Filters (run, person, changed by, dates in the company zone) live in the address (nuqs); a bad filter returns a message, not rows. Paged; only the page shown is decrypted.

## Encryption keys

Frozen pay rows (approved runs) cannot be re-encrypted, so **every old `FIELD_ENCRYPTION_KEYS` entry must be kept for good**. Despite what CLAUDE.md says about a re-encrypt job for other fields, no re-encrypt job exists in the code. If a key is lost, "Can't be read" appears on lines, payslips and history, blocks approval, and withholds totals: stop and check the keys before changing any rate.
